# 코드 작업 규칙

이 문서는 프로젝트의 모든 코드 작업에 적용되는 규칙이다. 목적은 코드 개발을 일관되고 지속 가능하게 유지하는 것이다. 전체 문서 목록은 [문서 인덱스](index.md)에서 확인한다.

## 1. 문서 우선 작업 절차

모든 코드 작업은 아래 순서를 따른다. 순서를 바꾸지 않는다.

1. [문서 인덱스](index.md)에서 작업과 관련된 문서를 찾아 읽는다.
2. 작업의 ID를 정하고 시작 처리를 한다. [로드맵](Roadmap.md)의 태스크나 [이슈](Issue.md)여야 하며, 없으면 먼저 등록한다. 상태 변경과 [진행 중](Ongoing.md) 기록은 [작업 관리 규칙](TaskRule.md#41-시작)을 따른다.
3. 작업 내용을 규정하는 문서가 없거나 부족하면, [문서 작업 규칙](DocumentationRule.md)에 따라 문서를 먼저 작성·수정한다.
   - 상세 설계 문서(`docs/design/`)에는 구현할 모듈, 클래스, 함수와 그 동작을 적는다. 코드에 아직 없는 심볼은 인라인 코드로 적는다. 코드에 없는 심볼로 코드 포인터 링크를 걸지 않는다.
4. 구현할 심볼의 목업을 만든다([포인터 규약](Traceability.md#8-목업-표시)). 목업은 심볼의 정의(이름과 시그니처)와 근거 문서로 가는 포인터, 목업 표시 `@stub: <작업 ID>`만 있고 본문은 비었거나 그 언어의 "미구현" 관용구다. 목업을 만든 심볼은 문서에서 인라인 코드를 코드 포인터 링크로 바꾼다. 이 단계에서 모든 검사가 통과하므로 진행 중 기록을 커밋할 수 있다. 목업을 만들어야 코드 작업이 진행 중이 된다.
5. 문서의 지시에 따라 목업을 구현하고, 다 구현한 심볼에서 `@stub:` 표시를 지운다. 남은 `@stub:` 표시가 "문서가 요구하지만 아직 구현되지 않은 것"의 목록이다. 새로 필요한 심볼도 4부터 같은 순서로 만든다.
6. [검증 도구](VerificationTools.md)를 모두 실행해 통과시킨다. `@stub:` 표시가 남아 있으면 작업을 완료할 수 없다.
7. [작업 관리 규칙](TaskRule.md#43-완료)에 따라 완료 처리를 한다.

코드를 먼저 바꾼 뒤 문서를 코드에 맞추는 일은 하지 않는다. 구현 중 문서와 다른 방식이 필요하다고 판단되면 코드 작성을 멈추고 문서부터 고친다.

## 2. 디렉터리 구조

모든 프로젝트에 공통인 경로는 다음과 같다. 그 밖의 디렉터리(제품 코드, 테스트, 빌드 설정 등)는 프로젝트의 **시스템 구조** 문서가 정한다. 시스템 구조 문서는 [문서 인덱스](index.md)의 제품 이해 절에 있다.

| 경로 | 용도 |
| --- | --- |
| `CLAUDE.md` | 진입 문서([문서 작업 규칙](DocumentationRule.md#7-진입-문서)). |
| `docs/` | 모든 문서. 코드 작업의 규칙이다. |
| `projinit.toml` | 검사기 설정([검증 도구의 설정](VerificationTools.md#11-설정)). |
| `.claude/` | Claude Code 프로젝트 설정. 검사기를 자동 실행하는 Stop hook([검증 도구](VerificationTools.md#9-일괄-실행과-자동-실행))과 첫 작업을 시작하는 `/start` 명령([첫 작업](TaskRule.md#48-첫-작업))을 둔다. |
| `.githooks/` | 저장소에 포함하는 git hook. `pre-commit`과 `commit-msg`를 둔다([커밋 규칙](CommitRule.md#5-강제)). |
| `.github/` | PR 템플릿과 CI([PR 규칙](PullRequestRule.md)). |

새로운 최상위 디렉터리가 필요하면 시스템 구조 문서의 디렉터리 표를 먼저 수정한다.

## 3. 언어와 스타일

개발 언어, 언어별 도구(버전 관리, 의존성 관리, 실행 방법), 이름 짓기와 형식은 시스템 구조 문서가 정한다. 언어와 무관하게 다음을 지킨다.

- 함수 하나는 한 가지 일만 한다. 같은 로직이 두 곳 이상에 생기면 공통 모듈로 옮긴다.
- 사용하지 않는 코드, 주석 처리된 코드는 남기지 않는다.
- 주석은 "무엇"이 아니라 "왜"를 적는다. 동작 설명은 문서에 있어야 한다.

## 4. 문서-코드 추적성

문서와 코드는 양방향 포인터로 연결한다. 형식과 규칙은 [포인터 규약](Traceability.md)을 따른다. 요약하면 다음과 같다.

- 문서는 마크다운 링크로 코드의 특정 심볼(구문 트리 단위)을 가리킨다. 개발 언어는 Python이 아니어도 된다.
- 코드는 docstring 또는 주석으로 근거 문서를 가리킨다.
- 모든 모듈과 공개 최상위 클래스·함수는 근거 문서를 가리켜야 한다.
- 한쪽 방향 포인터만 있는 상태는 허용하지 않는다.

## 5. 테스트

- 테스트의 위치, 이름, 프레임워크, 실행 명령은 시스템 구조 문서가 정한다. 실행 명령은 [검증 도구의 설정](VerificationTools.md#11-설정)에 프로젝트 명령으로 적어 일괄 검사가 함께 돌게 한다.
- 문서에 규정된 공개 동작마다 정상 경우와 실패 경우를 각각 하나 이상 테스트한다.
- 테스트도 코드이므로 [포인터 규약](Traceability.md)을 동일하게 적용한다. 테스트 모듈은 자신이 검증하는 동작을 규정한 문서를 가리킨다.

## 6. 검증과 완료 조건

코드 작업은 [검증 도구](VerificationTools.md#1-실행-방법)의 일괄 검사 `<projinit> check`가 성공(종료 코드 0)해야 완료로 본다. 이 명령은 모든 검사기와 프로젝트 명령(테스트 등)을 실행한다.

이 검사는 Stop hook과 pre-commit으로 자동 실행된다([검증 도구](VerificationTools.md#9-일괄-실행과-자동-실행)). 자동 실행에 기대지 않고, 작업을 끝내기 전에 직접 실행해 확인한다.

검증이 실패한 상태로 작업을 끝내지 않는다. 실패를 해결할 수 없으면 실패 내용을 그대로 보고한다.

## 7. 변경과 유지보수

- 동작을 바꾸려면 그 동작을 규정한 문서를 먼저 고친다. 그 다음 코드를 고친다.
- 심볼의 이름이나 위치를 바꾸면 [포인터 검사기](VerificationTools.md#4-포인터-검사기)가 깨진 포인터를 알려 준다. 문서의 포인터를 먼저 새 이름으로 고친 뒤 코드를 바꾼다.
- 심볼을 삭제하면 그 심볼을 가리키던 문서 내용도 함께 삭제하거나 고친다.
