# 포인터 규약

이 문서는 문서와 코드를 양방향으로 연결하는 포인터의 형식과 규칙을 정한다. 코드 작업 전반의 규칙은 [코드 작업 규칙](CodeRule.md)에, 이 규약을 검증하는 도구는 [검증 도구](VerificationTools.md#4-포인터-검사기)에 있다. 전체 문서 목록은 [문서 인덱스](index.md)에서 확인한다.

## 1. 목적

- **문서 → 코드 포인터**는 문서가 규정하는 내용이 코드의 정확히 어느 부분에 구현되는지 가리키는 화살표다.
- **코드 → 문서 포인터**는 코드가 어떤 문서를 근거로 작성되었는지 가리키는 화살표다.

줄 번호는 코드가 조금만 바뀌어도 어긋난다. 그래서 문서 → 코드 포인터는 줄 번호 대신 구문 트리의 심볼 이름으로 대상을 가리킨다. 검사기는 대상 파일을 [tree-sitter](https://tree-sitter.github.io/)로 파싱해 그 심볼이 실제로 존재하는지 확인한다.

이 규약은 개발 코드의 언어와 무관하다. 포인터의 형식은 모든 언어에서 같고, 언어마다 다른 것은 어떤 구문을 심볼로 보는지뿐이다. 그 차이는 [7. 언어별 심볼 규칙](#7-언어별-심볼-규칙)에 모아 둔다.

## 2. 문서에서 코드로 가는 포인터

마크다운 링크 문법을 그대로 쓴다. 링크 대상이 [7. 언어별 심볼 규칙](#7-언어별-심볼-규칙)에 있는 확장자의 파일이면 코드 포인터로 취급한다.

```markdown
[표시 이름](<코드 파일 상대 경로>#<한정 이름>)
```

- **경로**: 링크를 거는 문서 위치를 기준으로 한 상대 경로다. 일반 문서 링크와 같다.
- **한정 이름(qualified name)**: 파일 안에서 심볼에 이르는 이름을 `.`으로 이은 것이다. 언어가 `::` 같은 다른 구분자를 쓰더라도 포인터에서는 항상 `.`을 쓴다.
  - 최상위 정의: `main`, `ModuleIndex`
  - 안쪽 정의(메서드, 중첩 타입 등): `ModuleIndex.lookup`
  - 값(상수·변수·필드): `CONFIG_FILE`, `Link.source`
- **`#` 이후를 생략하면** 파일(모듈) 전체를 가리킨다.
- **줄 번호(`#L10` 등)는 금지**한다.
- 같은 한정 이름의 심볼이 한 파일에 여러 개 있으면(C++ 오버로드, 선언과 정의, getter와 setter 등) 포인터는 그 전체를 가리킨다.

예시 (`docs/` 아래 문서에서):

```markdown
링크 검사는 [check_links](../tools/check_docs.py#check_links)가 수행한다.
파서는 [Parser.parse](../src/parser.rs#Parser.parse)에 있다.
```

코드 블록과 인라인 코드 안의 링크는 예시로 보고 검사하지 않는다.

## 3. 코드에서 문서로 가는 포인터

`@doc:` 태그 뒤에 근거 문서의 경로를 적는다.

```text
@doc: <문서 경로>[#<제목 앵커>]
```

- **경로**: 저장소 루트 기준 경로다. 코드 파일의 위치와 무관하게 항상 같은 문자열로 같은 문서를 가리키도록 하기 위해서다. 예: `docs/VerificationTools.md`
- **제목 앵커**: 선택 사항이다. 문서의 제목에서 만든 앵커로, 만드는 방식은 [문서 작업 규칙](DocumentationRule.md#3-링크-규칙)의 앵커 규칙과 같다.
- 한 심볼에 여러 개를 달 수 있다. 태그 하나당 한 줄을 쓴다.

포인터는 **주석**에 쓴다. 모든 언어에 공통이다. Python은 **docstring**에도 쓸 수 있다.

### 3.1 주석

주석의 종류(`//`, `/* */`, `///`, `#` 등)는 가리지 않는다. 주석이 어느 심볼에 속하는지는 다음 순서로 정한다.

1. `@doc:` 주석은 코드와 같은 줄에 있으면 안 된다. 주석이 시작하는 줄이나 끝나는 줄에 코드가 있으면 오류다.
2. 주석 바로 아래 줄에서 심볼 정의가 시작하면 포인터는 그 심볼에 속한다. 사이에는 다른 주석 줄만 올 수 있고 빈 줄은 올 수 없다. 정의의 시작은 그 정의에 붙은 데코레이터·어트리뷰트·`export`·`template` 등을 포함한다. 한 줄에서 여러 심볼이 시작하면 첫 심볼에 속한다.
3. 2에 해당하지 않고 주석이 파일의 첫 코드보다 앞에 있으면 포인터는 파일(모듈)에 속한다. 파일 머리 주석이 이 경우다.
4. 어디에도 속하지 않으면 오류다.

```rust
//! @doc: docs/design/Parser.md

/// @doc: docs/design/Parser.md#2-토큰화
#[derive(Debug)]
pub struct Parser {}
```

### 3.2 Python docstring

모듈, 클래스, 함수의 docstring 안에 쓴다. 포인터는 그 docstring의 주인 심볼에 속한다.

```python
def check_links(root: Path) -> list[Problem]:
    """문서 링크의 대상 파일과 앵커가 존재하는지 검사한다.

    @doc: docs/VerificationTools.md#3-문서-링크-검사기
    """
```

## 4. 커버리지 규칙

코드 루트([설정](VerificationTools.md#11-설정)의 `code_roots`) 아래의 모든 코드 파일에 다음을 요구한다. 코드 파일은 [7. 언어별 심볼 규칙](#7-언어별-심볼-규칙)에 있는 확장자의 파일이다.

- 파일(모듈) 자체에 `@doc:` 포인터가 하나 이상 있어야 한다. 파일 머리 주석이나 Python 모듈 docstring에 쓴다.
- **공개 최상위 정의**는 자기 자신에게 `@doc:` 포인터가 하나 이상 있어야 한다.
  - 최상위: 파일 바로 아래, 또는 네임스페이스 역할의 구문(C++ `namespace`, Rust `mod`, TypeScript `namespace`) 바로 아래에 있다. 한정 이름을 붙여 바깥에서 정의한 것(C++ `void C::m() {}`)은 최상위가 아니다.
  - 정의: 함수·타입처럼 [7. 언어별 심볼 규칙](#7-언어별-심볼-규칙)에서 "정의"로 분류한 심볼이다. "값"으로 분류한 상수·변수·필드와 "네임스페이스"로 분류한 심볼은 제외한다.
  - 공개: 언어별 규칙에 따른다.

주석 말고 코드가 하나도 없는 파일(예: 빈 `__init__.py`)은 제외한다. 안쪽 심볼, 비공개 심볼, 값은 필수는 아니지만 필요하면 포인터를 달 수 있다.

## 5. 상호 참조 규칙

두 심볼이 같은 파일 안에 있고, 같은 심볼이거나 한쪽이 다른 쪽을 포함(조상·자손)하면 두 심볼은 **관련 있다**고 한다. 모듈 자체는 그 파일의 모든 심볼의 조상이다.

- 문서 D가 모듈(파일 전체)을 가리키면, 그 파일의 심볼 중 하나가 D를 가리켜야 한다.
- 문서 D가 모듈이 아닌 심볼 S를 가리키면, S와 관련 있는 심볼 중 **모듈이 아닌** 것이 D를 가리켜야 한다. 즉 S 자신, S를 감싸는 정의(클래스 등), S 안쪽의 심볼 중 하나다. 모듈 docstring이나 파일 머리 주석의 포인터는 여기에 해당하지 않는다. 그렇지 않으면 파일 머리의 포인터 하나로 그 파일의 모든 심볼이 검사를 통과해, 심볼 자신은 근거 문서를 모르는 상태가 된다.
- 심볼 S가 문서 D를 가리키면, D는 S와 관련 있는 심볼 중 하나를 가리켜야 한다. 이때는 모듈도 포함한다. 문서가 파일 전체를 가리키면 그 파일이 문서를 구현한다는 뜻이므로 파일 안 심볼의 포인터를 모두 받는다.

상호 참조를 판단할 때 앵커는 비교하지 않고 문서 파일만 비교한다. 이 규칙 때문에 한 방향 포인터만 있는 상태는 검증을 통과하지 못한다.

## 6. 검증

이 규약은 [포인터 검사기](VerificationTools.md#4-포인터-검사기)가 검증한다. 검사 항목은 다음과 같다.

1. 문서 → 코드 포인터: 대상 파일 존재, 줄 번호 금지, 구문 트리 상 심볼 존재.
2. 코드 → 문서 포인터: 대상 문서 존재, 앵커 존재, 주석 포인터의 소속 심볼 존재.
3. 코드 파일의 구문 오류.
4. [목업 표시](#8-목업-표시)의 작업 ID와 그 작업의 상태.
5. [커버리지 규칙](#4-커버리지-규칙).
6. [상호 참조 규칙](#5-상호-참조-규칙).

## 7. 언어별 심볼 규칙

각 언어에서 어떤 구문을 심볼로 등록하는지 정한다. 심볼은 정의, 값, 네임스페이스 셋 중 하나로 분류한다. 네임스페이스는 안쪽 심볼의 이름 앞에 붙을 뿐 커버리지 대상이 아니며, 그 바로 안쪽은 바깥과 같은 수준으로 본다. 표에 없는 구문(함수 본문 안의 지역 정의 등)은 심볼이 아니다. 단, Python은 함수 안의 클래스·함수도 등록한다. 새 언어를 지원하려면 이 절에 언어를 추가한 뒤 검사기를 고친다.

| 언어 | 확장자 | 정의 | 값 | 네임스페이스 | 이름 붙이기 | 공개 |
| --- | --- | --- | --- | --- | --- | --- |
| Python | `.py` | 클래스, 함수(함수 안의 것 포함) | 모듈·클래스 본문의 이름 대입(`x = …`, `x: T = …`) | 없음 | 데코레이터가 시작에 포함된다. | 이름이 `_`로 시작하지 않음 |
| JavaScript | `.js`, `.mjs`, `.cjs`, `.jsx` | 함수, 클래스, 메서드, 값이 함수·클래스인 변수 | 최상위 변수, 클래스 필드 | 없음 | `export`와 데코레이터가 시작에 포함된다. | `export`로 선언됨 |
| TypeScript | `.ts`, `.mts`, `.cts`, `.tsx` | JavaScript의 정의 + 인터페이스, 타입 별칭, enum, 함수 시그니처, 메서드 시그니처 | JavaScript의 값 + 인터페이스 속성, enum 멤버 | `namespace`, `declare module` | JavaScript와 같다. `declare module "x"`의 이름은 따옴표를 뺀 `x`다. | `export`로 선언됨 |
| Rust | `.rs` | 함수, 함수 시그니처, struct, enum, union, trait, 타입 별칭, `macro_rules!` | `const`, `static`, struct 필드, enum variant, trait의 연관 타입 | `mod` | `impl T`와 `impl Trait for T`의 항목은 `T.항목`이다(`T`는 제네릭 인자와 경로를 뺀 이름). 앞에 붙은 `#[…]` 어트리뷰트가 시작에 포함된다. `extern` 블록 안은 바깥과 같은 수준이다. | `pub` 계열 가시성이 있음 |
| C | `.c` | 함수 정의, 함수 선언, 이름 있는 struct·union·enum, `typedef` | 파일 수준 변수, struct 필드, enum 상수, `#define` 매크로 | 없음 | `#if`·`#ifdef` 블록(include guard 등) 안은 바깥과 같은 수준이다. | `static`이 아님 |
| C++ | `.cpp`, `.cc`, `.cxx`, `.h`, `.hpp`, `.hh`, `.hxx` | C의 정의 + class, 메서드 선언·정의, 생성자·소멸자·연산자, `using` 별칭 | C의 값 + 클래스 필드 | 이름 있는 `namespace` (`namespace a::b`는 `a`와 `a.b`) | `a::b::f`는 `a.b.f`, 소멸자는 `C.~C`, 연산자는 `operator==`처럼 쓴다. 바깥 정의 `void C::m()`도 `C.m`으로 등록한다. `template`이 시작에 포함된다. 이름 없는 `namespace`와 `extern "C"` 블록 안은 바깥과 같은 수준이다. `.h`는 C++로 파싱한다. | `static`이 아니고 이름 없는 `namespace` 안이 아님 |
| Go | `.go` | 함수, 메서드, 타입 선언(별칭 포함) | 파일 수준 `const`·`var` | 없음 | 메서드는 `리시버타입.메서드`다(포인터 `*`와 타입 인자를 뺀 이름). | 이름이 대문자로 시작함 |
| Java | `.java` | class, interface, enum, record, 어노테이션 타입, 메서드, 생성자 | 필드, 인터페이스 상수, enum 상수 | 없음 | 어노테이션은 선언에 포함된다. | `public`이 붙음 |

## 8. 목업 표시

목업은 아직 구현하지 않은 심볼의 정의만 먼저 만든 코드다. 목업이 있으면 문서 → 코드 포인터가 실제 심볼을 가리키므로 문서를 먼저 쓰는 단계에서도 검사가 통과한다. 절차는 [코드 작업 규칙](CodeRule.md#1-문서-우선-작업-절차)에 있다.

목업에는 그 목업을 구현할 작업의 ID를 표시한다.

```text
@stub: <작업 ID>
```

- `@doc:` 포인터를 다는 곳(주석, Python docstring)에 함께 쓴다. 한 줄에 하나를 쓴다.
- 표시한 작업은 [로드맵](Roadmap.md)이나 [이슈](Issue.md)에 있어야 하고, 상태가 진행 중(`[~]`)이어야 한다. 연결 작업이 있는 이슈는 연결 작업의 상태를 따른다.
- 그래서 목업을 다 구현해 표시를 지우기 전에는 작업을 완료(`[x]`)할 수 없고, 시작하지 않은 작업(`[ ]`)의 목업도 둘 수 없다.
- 코드 블록과 인라인 코드 안의 표시는 예시로 보지 않는다. 코드 파일 안의 주석과 docstring만 해석하므로 이 문서의 예시는 검사 대상이 아니다.
