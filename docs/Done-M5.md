# 완료 보관 M5 갱신

이 문서는 닫힌 마일스톤 M5의 완료 기록을 보관한다. 기록 형식은 [작업 관리 규칙](TaskRule.md#5-기록-형식)을 따르며, 아직 닫히지 않은 마일스톤의 기록은 [완료](Done.md)에 있다.

## M5-T1 `projinit upgrade` 명령 (버전 기록과 공통 파일 다시 만들기를 한 번에)

- 시작일: 2026-10-31
- 완료일: 2026-10-31
- 근거 문서: [템플릿 구성](design/Templates.md#10-갱신-명령)
- 관련 이슈: I16

### 계획
- `projinit upgrade`를 설계하고(템플릿 구성 10절) 목업을 만든 뒤 진행 중 커밋을 한다.
- 구현하고, 공통 작업 관리 규칙 4.9절을 "CLI로 올린 뒤 Claude가 이슈로 등록해 커밋한다"로 고친다(템플릿에서 고쳐 다시 만든다). README를 고친다.
- 버전을 `0.1.3`으로 올리고, 병합 뒤 `v0.1.3` 태그를 붙인다.

### 진행 기록
- 2026-10-31: 사용자가 "꼭 Claude에게 요청해야 하나, CLI로 업데이트하고 싶다, 0.1.2 이후에만 되는 거냐"고 물었다. 지금은 어느 버전에도 업데이트 명령이 없고, 새 버전 패키지에 명령이 있으면 이전 버전 프로젝트도 올릴 수 있다고 답했다. 사용자가 "프로젝트의 핵심 구조를 세팅하는 CLI이니 업데이트 명령이 있어야 한다"고 해서, 제품 비전 7절의 이후 기능 후보 "갱신"을 M5로 넣고 I16을 연결했다.
- 2026-10-31: 설계와 목업으로 진행 중 상태를 커밋했다(8f31440).
- 2026-10-31: `upgrade.py`, `projinit upgrade` 하위 명령, 테스트를 구현했다. 공통 작업 관리 규칙 4.9절을 "갱신 명령으로 올린 뒤 하나의 작업으로 등록해 커밋한다"로 고쳐 다시 만들고, README에 갱신 방법을 적었다. 버전을 `0.1.3`으로 올렸다.
- 2026-10-31: GitHub의 `v0.1.2`로 초기화해 커밋한 폴더에서 시험했다. 커밋하지 않은 변경이 있으면 거부했고, 정리한 뒤에는 `0.1.2 → 0.1.3`으로 설정과 공통 파일 7개가 한 번에 바뀌었다.
- 2026-10-31: M5의 유일한 태스크라 완료와 함께 M5를 닫고, 완료 문서의 기록(M5-T1, I14, I15)을 `docs/Done-M5.md`로 그대로 옮겼다.

### 결정 사항
- 커밋하지 않은 변경이 있으면 갱신을 거부한다. I15에서 본 것처럼 갱신이 진행 중인 작업과 섞이지 않게 하기 위해서다.
- 실행 명령이 지정된 프로젝트(이 저장소, 미리 써 보기 설정)는 버전을 고정하지 않으므로 갱신을 거부하고 `init --refresh-common`을 쓰게 한다.
- 갱신 명령은 커밋하지 않는다. 바뀐 파일은 그 프로젝트의 작업으로 등록해 커밋하게 안내한다.

### 변경 파일
- `docs/ProductVision.md`, `docs/Roadmap.md`, `docs/Issue.md`, `docs/design/Templates.md`, `docs/design/Checkers.md`, `docs/Ongoing.md`
- 추가: `src/projinit/upgrade.py`(신규), `src/projinit/cli.py`, `tests/test_upgrade.py`(신규), `tests/test_cli.py`, `src/projinit/templates/docs/TaskRule.md`, `docs/TaskRule.md`, `README.md`, `pyproject.toml`, `uv.lock`, `docs/Done.md`, `docs/Done-M5.md`(신규)

### 결과
- `uvx --from <source>@v<새 버전> projinit upgrade` 한 번으로 이미 초기화한 프로젝트를 새 버전으로 갱신한다. 이 명령이 들어간 버전(`v0.1.3`)부터 그 이전 버전으로 초기화한 모든 프로젝트에 쓸 수 있다.
- 갱신이 진행 중인 작업과 섞이지 않도록 커밋하지 않은 변경이 있으면 거부하고, 끝나면 Claude에게 커밋을 맡기라고 안내한다.
- M5(갱신)가 닫혔다. 병합 뒤 `v0.1.3` 태그를 붙인다.

## I15 초기화된 프로젝트에서 ProjInit 버전을 올리는 절차가 공통 규칙에 없어 규칙 밖에서 업그레이드가 일어나는 문제

- 시작일: 2026-10-31
- 완료일: 2026-10-31
- 근거 문서: [작업 관리 규칙](TaskRule.md)

### 계획
- 공통 작업 관리 규칙에 "ProjInit 버전 올리기" 절차를 더한다(템플릿에서 고쳐 다시 만든다).
- README의 업그레이드 안내를 "그 프로젝트의 Claude에게 요청한다"로 바꾼다.
- 버전을 `0.1.2`로 올리고 병합 뒤 `v0.1.2` 태그를 붙인다.

### 진행 기록
- 2026-10-31: 사용자가 `Jjabtero`(v0.1.0으로 초기화한 프로젝트)에서 내 안내대로 터미널에서 `version`을 바꾸고 `--refresh-common`을 실행했다. 그 사이 그 프로젝트의 Claude는 `i1-remote-repository` 브랜치에서 I1을 하고 있었고, 자기가 만들지 않은 공통 파일 변경(설정, hook, CI, 작업 관리 규칙 4.8절)을 발견해 어떻게 처리할지 물었다. 사용자가 "왜 이런 상황이 나온 거냐"고 물었다.
- 2026-10-31: 원인은 두 가지였다. 업그레이드를 그 프로젝트의 작업 ID 밖에서 하라고 안내한 내 잘못, 그리고 공통 규칙에 ProjInit 버전을 올리는 절차가 없어 그 프로젝트의 Claude가 정상 업그레이드인지 알 수 없었던 빈틈이다. 사용자가 이슈로 등록하고 고치라고 했다.
- 2026-10-31: 같은 대화에서 그 프로젝트의 Stop hook 실패는, 그쪽 Claude가 원격 주소를 설정에 적고 `--refresh-common`을 실행하지 않아 템플릿 일치 검사가 잡은 것이었다. 검사기는 의도대로 동작했다.
- 2026-10-31: 진행 중 기록을 먼저 커밋했다(3acd7f8). I14에서 커밋하지 않은 기록을 잃을 뻔한 일을 되풀이하지 않기 위해서다.
- 2026-10-31: 작업 관리 규칙 템플릿에 4.9절 "ProjInit 버전 올리기"를 더하고 `--refresh-common`으로 반영했다. README의 업그레이드 안내를 "그 프로젝트의 Claude에게 요청한다"로 바꾸고, 버전을 `0.1.2`로 올렸다.

### 결정 사항
- 버전 올리기도 하나의 작업이다. 이슈로 등록하고 작업 브랜치에서 하며, 다른 작업과 커밋을 나눈다.
- 공통 파일은 이 절차 밖에서 고치지 않는다. 작업 중 자기가 만들지 않은 공통 파일 변경을 발견하면 사용자에게 업그레이드인지 묻는다.

### 변경 파일
- `docs/Issue.md`, `docs/Ongoing.md`
- 추가: `src/projinit/templates/docs/TaskRule.md`, `docs/TaskRule.md`, `README.md`, `pyproject.toml`, `uv.lock`, `docs/Done.md`

### 결과
- 초기화된 프로젝트의 Claude가 ProjInit 버전 올리기를 이슈로 등록한 하나의 작업으로 처리하고, 바뀐 규칙을 사용자에게 알린다.
- 출처를 모르는 공통 파일 변경을 발견하면 업그레이드인지 사용자에게 묻도록 규칙에 적었다.
- 병합 뒤 `v0.1.2` 태그를 붙인다.

### 검증
- `uv run projinit check`: 모두 통과

## I14 첫 작업(`/start`)이 질문 목록을 한꺼번에 내밀어 모두 답해야 할 것처럼 느껴지는 문제

- 시작일: 2026-10-31
- 완료일: 2026-10-31
- 근거 문서: [작업 관리 규칙](TaskRule.md#48-첫-작업)

### 계획
- 첫 작업 절차를 "한 가지만 가볍게 묻고, 나머지는 대화하며 하나씩, 모두 선택 사항"으로 고친다(템플릿에서 고쳐 다시 만든다).
- 미결정이 남아 있어도 첫 작업을 끝낼 수 있음을 적는다.
- 새 프로젝트가 받을 수 있게 버전을 `0.1.1`로 올리고, 병합 뒤 `v0.1.1` 태그를 붙인다.

### 진행 기록
- 2026-10-31: `/start`로 시작한 사용자가 "필수 기능을 왜 물어보는지 모르겠다. 선택 사항이어도 되나? 반드시 답해야 할 것처럼 물어보니까 시작하기 두렵다"고 했다. Claude가 첫 작업 절차 2단계에 나열한 항목(목적, 쓰는 사람, 필수 기능, 언어와 기술 스택, 원격 저장소)을 번호 붙은 질문 목록으로 한꺼번에 낸 것이 원인이었다.
- 2026-10-31: PR #9가 열려 있어 `m2-t7-release` 위에 `i14-gentle-start`를 쌓았다. 템플릿(작업 관리 규칙, `/start` 명령)을 고쳐 `--refresh-common`으로 반영했다.
- 2026-10-31: README가 릴리스 전 상태("`v0.1.0`은 아직 나오지 않았다", 미리 써 보기)로 남아 있어, 설치 명령을 `v0.1.1`로 바꾸고 미리 써 보기 절을 "이미 초기화한 프로젝트를 새 버전으로"로 바꿨다. 첫 실행이 오래 걸리는 이유와 `/start`가 한 가지만 묻는다는 점도 적었다.
- 2026-10-31: 완료로 옮기는 스크립트가, 진행 중 문서에서 이 기록을 지운 뒤 완료 문서에 넣을 자리를 찾다가 실패했다. M2를 보관한 뒤라 완료 문서에 기록이 하나도 없어 `## `를 찾지 못한 것이다. 커밋하지 않은 기록이라 기록 보존 검사의 보호 밖이었고, 작성해 둔 내용으로 이 완료 기록을 다시 썼다. 진행 중 기록을 작업 도중에 커밋해 두라는 규칙(작업 관리 규칙 4.5절)을 이번 작업에서 지키지 않은 탓이다.

### 결정 사항
- 첫 질문은 하나("어떤 걸 만들고 싶은지")만 하고, 모르는 것은 정하지 않아도 된다고 알린다. 나머지는 모두 선택 사항이며 대화하며 하나씩 묻는다.
- 버전을 `0.1.1`로 올린다. 이미 `0.1.0`으로 초기화한 프로젝트는 설정의 `version`을 바꾸고 `init --refresh-common`을 실행하면 새 절차를 받는다.

### 변경 파일
- `src/projinit/templates/docs/TaskRule.md`, `src/projinit/templates/.claude/commands/start.md`, `docs/TaskRule.md`, `.claude/commands/start.md`, `pyproject.toml`, `uv.lock`, `README.md`, `docs/Issue.md`, `docs/Ongoing.md`
- 추가: `docs/Done.md`

### 결과
- `/start`는 "어떤 걸 만들고 싶은지" 한 가지만 묻고, 나머지는 대화하며 하나씩 선택적으로 묻는다. 미결정이 남아도 첫 작업을 끝낼 수 있다.
- 버전이 `0.1.1`이 되었고, README가 릴리스된 상태를 안내한다. 병합 뒤 `v0.1.1` 태그를 붙인다.

- `uv run projinit check`: 모두 통과
