# 검증 도구

이 문서는 문서와 코드의 규칙 준수를 자동으로 검증하는 도구(ProjInit 검사기)가 무엇을 검사하고 어떻게 실행되는지 정한다. 검증하는 규칙은 [문서 작업 규칙](DocumentationRule.md), [포인터 규약](Traceability.md), [작업 관리 규칙](TaskRule.md)과 이 문서의 [자동 실행](#9-일괄-실행과-자동-실행) 규칙이다. 검사기는 프로젝트에 복사하지 않고 버전을 고정해 실행하며, 그 버전과 경로는 [설정](#11-설정)에 있다. 전체 문서 목록은 [문서 인덱스](index.md)에서 확인한다.

## 1. 실행 방법

검사기는 `projinit` 명령이다. 프로젝트에서 이 명령을 어떻게 부르는지는 [설정](#11-설정)의 실행 명령이 정한다. 아래에서 `<projinit>`은 그 명령을 뜻한다.

```sh
<projinit> check                         # 모든 검사와 설정의 프로젝트 명령(테스트 등)을 한 번에 실행
<projinit> check --hook stop             # Claude Code Stop hook이 실행
<projinit> check --hook pre-commit       # git pre-commit hook이 실행
<projinit> commit-msg <메시지 파일>       # git commit-msg hook이 실행
<projinit> commits --subject <PR 제목> --branch <브랜치>   # CI가 PR에서 실행
<projinit> pr-order --pr <번호> --open-prs <파일>         # CI가 PR에서 실행
```

- 문제가 없으면 종료 코드 0으로 끝나고 통과 요약을 출력한다.
- 문제가 있으면 문제마다 `<저장소 기준 경로>:<줄>: <메시지>` 형식으로 한 줄씩 출력하고 종료 코드 1로 끝난다.
- 모든 명령은 `--root <경로>`로 검사할 저장소 루트를 바꿀 수 있다. 기본값은 현재 디렉터리다.
- 설정 파일에 오류가 있으면 그것을 문제로 보고하고 종료 코드 1로 끝난다.

`check`가 실행하는 검사는 [3. 문서 링크 검사기](#3-문서-링크-검사기), [4. 포인터 검사기](#4-포인터-검사기), [6. 작업 관리 검사기](#6-작업-관리-검사기), [8. 강제 장치 검사기](#8-강제-장치-검사기), [10. 커밋 메시지 검사기](#10-커밋-메시지-검사기)의 이력 검사, [14. 템플릿 일치 검사기](#14-템플릿-일치-검사기) 순서이며, 그 뒤에 [5. 테스트](#5-테스트)의 프로젝트 명령을 실행한다. 하나가 실패해도 나머지를 실행한다.

## 2. 공통 모듈

모든 검사기가 같은 방식으로 파일을 찾고 문서를 읽는다.

- **검사 대상 문서**: 진입 문서, 루트의 `README.md`(있으면), 문서 디렉터리 아래의 모든 `.md` 파일이다. `README.md`는 링크만 검사하고 고아 문서 판정에는 넣지 않는다.
- **검사 대상 코드 파일**: 설정의 코드 루트 아래에서 [포인터 규약](Traceability.md#7-언어별-심볼-규칙)의 언어 표에 있는 확장자를 가진 파일이다. 없는 코드 루트는 건너뛴다.
- **링크**: 마크다운 링크 `[이름](대상)`이다. 이미지 링크, 코드 블록과 인라인 코드 안의 링크, `http://`·`https://`·`mailto:`로 시작하는 외부 링크는 검사하지 않는다.
- **앵커**: 제목에서 [문서 작업 규칙](DocumentationRule.md#3-링크-규칙)의 규칙으로 만든다.

## 3. 문서 링크 검사기

[문서 작업 규칙](DocumentationRule.md)의 링크 규칙, 고아 문서 금지, 진입 문서 형식을 검사한다.

- 문서의 링크 대상 파일이나 디렉터리가 있어야 한다. 대상이 `.md` 문서이고 앵커가 있으면 그 문서에 앵커가 있어야 한다. 코드 파일 링크는 [포인터 검사기](#4-포인터-검사기)가 검사한다.
- 진입 문서가 있고, 인덱스로 가는 링크가 있어야 한다.
- 진입 문서가 [진입 문서 형식](DocumentationRule.md#7-진입-문서)을 지켜야 한다.
- 문서 디렉터리 아래의 모든 문서가 인덱스에서 링크를 따라 도달할 수 있어야 한다.

## 4. 포인터 검사기

[포인터 규약](Traceability.md)을 검사한다. 검사 항목은 [포인터 규약의 검증](Traceability.md#6-검증)에 있다.

- 코드 루트 밖의 코드 파일도 문서가 가리키면 분석한다.
- 통과 요약에는 문서 → 코드, 코드 → 문서 포인터 수와 남은 [목업](Traceability.md#8-목업-표시) 수를 적는다. 남은 목업 수가 "문서가 요구하지만 아직 구현되지 않은 것"의 수다.

## 5. 테스트

프로젝트의 자동 테스트는 검사기가 아니라 프로젝트 자신의 명령으로 실행한다. 그 명령은 [설정](#11-설정)의 프로젝트 명령에 적고, `check`가 검사기들 다음에 차례로 실행한다. 개발 언어에 맞는 명령을 쓴다(예: `cargo test`, `npm test`, `uv run python -m unittest`).

- 명령은 루트에서 셸로 실행하며, 명령 문자열이 그 검사의 이름이 된다.
- 종료 코드가 0이 아니면 실패다.

## 6. 작업 관리 검사기

[작업 관리 규칙](TaskRule.md)을 작업 ID 기준으로 검사한다. 해석하는 문서 형식은 [작업 관리 규칙의 문서 형식](TaskRule.md#6-문서-형식)에 있다.

- 로드맵·이슈의 형식과 번호, ID 중복.
- 상태와 진행 중·완료 기록의 대응, 연결 작업, [경량 이슈](TaskRule.md#46-가벼운-작업-경로).
- 기록의 필수 필드·절, 날짜 형식, 완료 기록 순서, 진행 중 문서의 `없음` 규칙.
- [완료 보관](TaskRule.md#66-완료-보관)의 이름·위치·중복.
- [기록 보존](TaskRule.md#65-기록-보존-검사): git의 마지막 커밋과 비교한다. git 저장소가 아니면 건너뛴다.
- 작업 관리 문서와 보관 문서 본문에 나온 작업 ID가 모두 있는지.

## 7. 코드 분석 모듈

포인터 검사기는 코드 파일을 [tree-sitter](https://tree-sitter.github.io/)로 파싱한다. 그래서 개발 언어와 무관하게 같은 포인터 형식을 쓴다.

- 지원 언어와 언어별로 무엇을 심볼로 보는지는 [포인터 규약의 언어별 심볼 규칙](Traceability.md#7-언어별-심볼-규칙)에 있다.
- 언어별 문법은 검사기 패키지에 들어 있어서 실행할 때 내려받지 않는다.
- 구문 오류가 있는 파일은 첫 오류 위치에 `파싱 실패`를 보고하고 그 파일의 심볼은 없는 것으로 본다.

## 8. 강제 장치 검사기

[9. 일괄 실행과 자동 실행](#9-일괄-실행과-자동-실행)의 장치가 설치되어 있는지 검사한다. 장치가 빠지면 검사기가 자동으로 돌지 않는데, 그 사실을 아무도 모르게 되는 것을 막는다.

- `.claude/settings.json`에 Stop 명령을 실행하는 command hook이 있어야 한다.
- `.githooks/pre-commit`, `.githooks/commit-msg`가 있고, 실행 권한이 있으며, 각 명령을 담고 있어야 한다.
- git 설정 `core.hooksPath`가 `.githooks`여야 한다. 이 설정은 저장소에 포함되지 않아 클론할 때마다 한 번 해 줘야 하므로, 빠뜨리면 이 검사가 알려 준다.

각 장치가 실행해야 하는 명령은 설정의 실행 명령 `<projinit>`으로 만든다.

| 장치 | 명령 |
| --- | --- |
| Stop hook | `cd "$CLAUDE_PROJECT_DIR" && <projinit> check --hook stop` |
| pre-commit | `<projinit> check --hook pre-commit` |
| commit-msg | `<projinit> commit-msg "$1"` |

설정에서 실행 명령을 만들 수 없으면(실행 명령도, 출처와 버전도 없으면) 그것을 설정 파일의 문제로 보고한다.

## 9. 일괄 실행과 자동 실행

검사기를 작업자의 기억에 맡기지 않고 자동으로 실행한다. 장치는 네 가지이며 서로 다른 구멍을 막는다.

| 장치 | 실행 시점 | 실패하면 |
| --- | --- | --- |
| Claude Code Stop hook | Claude가 턴을 끝내려 할 때 | 첫 시도에서는 턴 종료를 막고 실패 요약을 Claude에게 돌려준다. 이미 한 번 막힌 뒤의 종료(`stop_hook_active`)는 허용하고, 남은 실패를 사용자에게 경고로 보여 준다. |
| git pre-commit | 사람이든 Claude든 커밋하려 할 때 | 커밋을 거부한다. |
| git commit-msg | 커밋 메시지를 확정할 때 | [커밋 메시지 형식](CommitRule.md#3-메시지-형식)을 어기면 커밋을 거부한다. |
| [CI](#12-ci) | PR을 열거나 갱신할 때, `main`에 push될 때 | 검사가 실패한 PR은 병합하지 않는다([PR 규칙](PullRequestRule.md#4-병합)). |

- Stop hook이 두 번째 종료를 허용하는 이유: [코드 작업 규칙](CodeRule.md#1-문서-우선-작업-절차)상 작업 중에 사용자에게 질문하며 턴을 끝내야 할 때가 있기 때문이다. 이때 Claude는 실패를 고치거나, 남긴 이유를 사용자에게 보고해야 한다.
- 실패 요약에는 실패한 검사마다 이름과 출력의 마지막 40줄을 담는다.
- pre-commit은 스테이징한 내용이 아니라 작업 트리를 검사한다.

## 10. 커밋 메시지 검사기

[커밋 규칙](CommitRule.md)의 메시지 형식과 [PR 규칙](PullRequestRule.md)의 브랜치 이름·PR 제목을 검사한다. 세 가지로 쓴다.

| 검사 | 명령 | 대상 | 작업 상태 확인 |
| --- | --- | --- | --- |
| 이력 검사 | `<projinit> check`에 포함 | 설정의 기준 커밋 이후의 병합이 아닌 모든 커밋 | ID 존재만 확인 |
| 커밋 시점 검사 | `<projinit> commit-msg <파일>` | 작성 중인 커밋 메시지 하나 | ID가 `[~]` 또는 `[x]`인지까지 확인 |
| PR 검사 | `<projinit> commits --subject <PR 제목> --branch <브랜치>` | PR 제목과 작업 브랜치 이름 | 제목은 시작 여부까지, 브랜치는 ID 존재만 확인 |

이력 검사에서 작업 상태를 확인하지 않는 이유는, 지금 문서의 상태가 그 커밋 당시의 상태와 다를 수 있기 때문이다. 작업 ID는 지워지지 않으므로 존재 여부는 지금 문서로 확인할 수 있다.

메시지 검사 항목:

- `#`으로 시작하는 줄(git 주석)은 무시한다. 빈 메시지는 문제다.
- `Merge `, `Revert `, `fixup! `, `squash! `로 시작하는 제목은 통과한다.
- 제목 형식(`<작업 ID>[, <작업 ID>…][(진행 중)]: <요약>`), 72자를 넘는 제목, 마침표로 끝나는 요약, 제목 다음 줄이 비어 있지 않음, 제목 안의 중복 ID, 로드맵·이슈에 없는 ID를 보고한다.
- PR 제목에 `(진행 중)`이 있으면 문제다.
- 브랜치 이름은 `<작업 ID 소문자>-<설명>`(설명은 영문 소문자·숫자를 `-`로 이음)이어야 하고, 그 작업 ID가 로드맵·이슈에 있어야 한다.

## 11. 설정

검사기 설정은 저장소 루트의 `projinit.toml`이다. 파일이 없거나 키가 빠지면 기본값을 쓴다.

```toml
[projinit]
version = "0.1.0"        # 이 프로젝트가 쓰는 ProjInit 버전 (git 태그 v0.1.0)
source = "git+https://github.com/qazcdesnu/ProjInit"   # 설치 출처
command = ""             # 실행 명령. 비우면 version과 source로 만든다

[paths]
docs = "docs"            # 문서 디렉터리
entry = "CLAUDE.md"      # 진입 문서
code_roots = ["src", "tests"]   # 코드 루트

[check]
commands = []            # check가 검사기 다음에 실행할 프로젝트 명령 (테스트 등)
commit_baseline = ""     # 커밋 이력 검사의 기준 커밋. 비우면 모든 커밋을 검사한다

[template]
repository = "git@github.com:me/my-project.git"   # 공통 문서의 빈 자리 repository에 들어갈 값
```

- `[template]` 표의 값은 공통 규칙 문서의 빈 자리(`{{이름}}`)를 채운다. 키는 자유롭게 쓰되 값은 문자열이어야 한다.
- 실행 명령 `<projinit>`은 `projinit.command`다. 비어 있으면 `uvx --from <source>@v<version> projinit`이다.
- 인덱스는 문서 디렉터리의 `index.md`이고, 작업 관리 문서(`Roadmap.md`, `Issue.md`, `Ongoing.md`, `Done.md`, `Done-M<n>.md`)도 문서 디렉터리에 있다. 이 이름들은 공통 규칙이 정하므로 설정하지 않는다.
- 설정 파일이 TOML로 읽히지 않거나, 모르는 표나 키가 있거나, 값의 형이 틀리면 설정 오류다. 오타로 설정이 조용히 무시되지 않게 하기 위해서다. 설정 오류는 `projinit.toml:<줄>: 설정 오류: <메시지>`로 보고한다.

## 12. CI

`.github/workflows/verify.yml`은 GitHub Actions에서 검증을 실행한다. [PR 규칙](PullRequestRule.md#5-ci)이 이 CI를 쓴다.

- 실행 시점: PR이 열리거나 갱신될 때, `main`에 push될 때.
- 커밋 이력 검사가 기준 커밋까지 볼 수 있도록 전체 이력을 받는다(`fetch-depth: 0`).
- uv를 설치한 뒤 `git config core.hooksPath .githooks`를 실행하고 `<projinit> check`를 실행한다. CI의 저장소 사본에는 이 git 설정이 없어서, 이 단계가 없으면 [강제 장치 검사기](#8-강제-장치-검사기)가 실패한다.
- PR에서는 PR 제목과 브랜치 이름을 [커밋 메시지 검사기](#10-커밋-메시지-검사기)의 PR 검사로, 앞선 열린 PR 포함 여부를 [PR 순서 검사기](#13-pr-순서-검사기)로 확인한다. 열린 PR 목록은 GitHub CLI(`gh pr list`)와 워크플로의 `GITHUB_TOKEN`으로 받는다.
- CI는 Linux에서 돈다. 파일 이름의 대소문자를 구분하므로, macOS에서 통과한 대소문자가 다른 링크도 여기서 실패한다.

PR 본문 템플릿은 `.github/pull_request_template.md`다.

## 13. PR 순서 검사기

[PR 규칙](PullRequestRule.md#4-병합)의 "PR 번호 순서대로 병합하면 충돌이 없다"를 지키기 위해, 검사하는 PR이 번호가 앞선 열린 PR의 커밋을 모두 포함하는지 확인한다. CI의 PR 실행에서만 쓴다.

```sh
gh pr list --state open --json number,headRefName,headRefOid > open-prs.json
<projinit> pr-order --pr <PR 번호> --open-prs open-prs.json
```

- 열린 PR 중 번호가 검사하는 PR보다 작고, 그 PR의 마지막 커밋이 `HEAD`의 조상이 아닌 PR을 보고한다. 커밋이 저장소에 없어도 포함하지 않은 것으로 본다.
- 문제는 `PR #<검사하는 번호>:1: PR #<번호> (<브랜치>)를 포함하지 않음`으로 출력한다.

## 14. 템플릿 일치 검사기

공통 규칙 문서와 강제 장치 파일(공통 파일)은 설정의 `version`에 해당하는 ProjInit 템플릿에서 만든 것이다. 문서와 검사기는 한 쌍이므로 둘이 어긋나지 않는지 검사한다.

- **템플릿 일치**: 공통 파일마다, 실행 중인 검사기의 템플릿을 설정 값으로 채운 결과와 내용이 같아야 한다. 공통 파일을 손으로 고쳤거나, 설정의 버전만 올린 경우에 걸린다. 공통 규칙을 바꾸려면 ProjInit의 템플릿을 고치고 `<projinit> init --refresh-common`으로 다시 만든다. 빈 자리에 넣을 값이 설정에 없으면 그것을 문제로 보고한다.
- **버전 일치**: 실행 중인 검사기의 버전이 설정의 `version`과 같아야 한다. 설정에 실행 명령(`projinit.command`)이 지정되어 있으면 버전을 고정하지 않는 것으로 보고 건너뛴다.
