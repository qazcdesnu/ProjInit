# 작업 관리 규칙

이 문서는 할 일을 계획하고, 진행 상황과 완료 내역을 기록하는 규칙을 정한다. 문서와 코드를 작성하는 규칙은 [문서 작업 규칙](DocumentationRule.md)과 [코드 작업 규칙](CodeRule.md)에 있다. 전체 문서 목록은 [문서 인덱스](index.md)에서 확인한다.

## 1. 작업 관리 문서

| 문서 | 용도 | 적는 수준 |
| --- | --- | --- |
| [로드맵](Roadmap.md) | 계획된 할 일 목록과 상태 | 태스크당 한 줄 |
| [진행 중](Ongoing.md) | 지금 하고 있는 작업의 상세 내역 | 상세 |
| [완료](Done.md) | 끝난 작업의 상세 기록. 아직 닫히지 않은 마일스톤의 기록을 둔다. | 상세 |
| 완료 보관 (`docs/Done-M<n>.md`) | 닫힌 마일스톤 n의 완료 기록. [완료](Done.md)의 머리말에서 링크한다. | 상세 |
| [이슈](Issue.md) | 작업 중 발생한 문제, 계획과 별도로 사용자가 지시한 요구사항 | 이슈당 짧은 설명 |

로드맵과 이슈에는 무엇을 할지만 간단히 적는다. 어떻게 했는지, 무엇이 바뀌었는지는 진행 중과 완료에만 적는다.

## 2. 작업 ID

| 형식 | 의미 | 예 |
| --- | --- | --- |
| `M<n>-T<m>` | 마일스톤 n의 태스크 m. 로드맵에 있는 할 일. | `M1-T3` |
| `I<n>` | 이슈. 작업 중 발견한 문제, 계획과 별도로 사용자가 지시한 요구사항. | `I2` |
| `H<n>` | 핫픽스. 바로 고쳐야 하는 결함. | `H1` |

- 번호는 1부터 차례로 붙이며, 한 번 쓴 ID는 지우거나 다시 쓰지 않는다.
- 기존 태스크 사이에 할 일이 생기면 그 마일스톤의 다음 번호를 붙여 맨 뒤에 추가한다. 번호를 다시 매기지 않는다.
- 커밋 메시지, 진행 중·완료 기록에서 작업을 가리킬 때 이 ID를 쓴다. 커밋 메시지 형식은 [6.7 커밋 메시지](#67-커밋-메시지)에 있다.
- 문서 작업이든 코드 작업이든 모든 작업은 이 ID 중 하나로 시작하고 끝낸다. 해당하는 ID가 없으면 먼저 [로드맵](Roadmap.md)이나 [이슈](Issue.md)에 등록한다.

## 3. 상태 표기

로드맵과 이슈의 각 줄은 상태 표시로 시작한다.

| 표기 | 상태 | 진행 중 문서 | 완료 문서 |
| --- | --- | --- | --- |
| `[ ]` | 아직 하지 않음 | 없음 | 없음 |
| `[~]` | 진행 중 | 상세 내역 있음 | 없음 |
| `[x]` | 완료 | 없음 | 상세 기록 있음 |

이 세 문서의 상태는 항상 서로 맞아야 한다. 예외는 [4.6 가벼운 작업 경로](#46-가벼운-작업-경로)의 경량 이슈로, 진행 중·완료 기록 없이 이슈 줄에 결과와 완료일을 적는다.

## 4. 작업 흐름

### 4.1 시작

1. 로드맵(또는 이슈)에서 해당 줄을 `[ ]`에서 `[~]`로 바꾼다.
2. [진행 중](Ongoing.md)에 [5. 기록 형식](#5-기록-형식)의 항목을 추가하고 계획을 적는다.
3. 근거가 되는 상세 설계 문서가 없으면 먼저 작성한다. 코드 작업이면 구현할 심볼의 목업을 만들고, 목업이 생긴 심볼만 코드 포인터 링크로 바꾼다. 절차는 [코드 작업 규칙](CodeRule.md#1-문서-우선-작업-절차)에 있다.

### 4.2 진행

- 작업하는 동안 진행 중 항목의 진행 기록, 변경 파일, 결정 사항을 갱신한다.
- 진행 기록과 결정 사항에는 줄을 덧붙이기만 한다. 이미 적은 줄은 고치거나 지우지 않고, 바로잡을 내용은 새 줄로 덧붙인다. 계획과 변경 파일은 고칠 수 있다.
- 작업 중 계획 밖의 문제가 생기거나 사용자가 계획과 별도로 무언가를 지시하면 [이슈](Issue.md)에 등록한다. 지금 작업 안에서 바로 처리하는 경우에도 등록하고, 처리 내역은 진행 중 항목에 함께 적는다.

### 4.3 완료

1. [검증 도구](VerificationTools.md)를 모두 통과시킨다.
2. 진행 중 항목을 [완료](Done.md)의 맨 위로 옮기고, 완료일·결과·검증 결과를 채운다. 진행 중 항목의 줄은 하나도 고치거나 빼지 않고 그대로 옮기며, 필요한 내용은 줄을 덧붙여 적는다.
3. 진행 중 문서에서 그 항목을 지운다. 진행 중인 작업이 없으면 진행 중 문서는 "없음"만 남는다.
4. 로드맵(또는 이슈)의 줄을 `[x]`로 바꾼다.

### 4.4 취소와 이관

- 진행 중 기록은 지우지 않는다. 그만두는 작업은 아래의 취소로 처리해 기록을 완료로 옮긴다.
- 하지 않기로 한 태스크는 줄을 지우지 않는다. `[x]`로 바꾸고 줄 끝에 `(취소)`를 붙이며, 완료 문서에 취소 사유를 적는다.
- 이슈를 다른 작업이 처리하는 경우(로드맵 태스크로 옮기거나 진행 중인 다른 작업 안에서 처리)에는 이슈 아래에 `- 연결 작업: <작업 ID>` 줄을 적는다. 이때 이슈는 자체 진행 중·완료 기록을 두지 않고, 상태를 연결 작업과 항상 같게 맞춘다. 처리 내역은 연결 작업의 기록에 적고, 그 기록의 `관련 이슈` 필드에 이슈 ID를 적는다.

### 4.5 기록 보존

진행 중·완료 기록은 작업의 세부 내역을 남기는 유일한 곳이다. 옮기거나 고치다가 내용이 빠지면 되살릴 방법이 없으므로, 다음을 지킨다.

- 진행 중 기록의 진행 기록·결정 사항, 그리고 완료 기록은 줄을 덧붙이기만 한다([4.2 진행](#42-진행)).
- 진행 중 기록을 완료로 옮길 때 모든 줄을 그대로 옮긴다([4.3 완료](#43-완료)).
- 진행 중 기록을 지우지 않는다([4.4 취소와 이관](#44-취소와-이관)).

[작업 관리 검사기](VerificationTools.md#6-작업-관리-검사기)가 마지막 커밋과 비교해 이를 검사한다([6.5 기록 보존 검사](#65-기록-보존-검사)). 비교 기준이 커밋이므로, 진행 중 기록은 작업 도중에도 커밋해 두어야 보호된다.

### 4.6 가벼운 작업 경로

오타 하나를 고치는 데도 진행 중·완료 기록의 모든 절을 채우면 절차가 작업보다 무거워진다. 아래 조건을 모두 만족하는 작업은 진행 중·완료 기록 없이 [이슈](Issue.md)의 줄 하나로 처리한다. 이것을 **경량 이슈**라고 한다.

**조건**

- 로드맵 태스크가 아니라 이슈(`I`, `H`)다.
- 커밋 하나로 끝난다.
- 판단이나 결정이 필요 없다. 무엇을 어떻게 고칠지가 처음부터 분명하다.
- 규칙·형식·검사기의 동작과 제품 코드의 동작을 바꾸지 않는다.
- 예: 오타·어색한 문장 고치기, 깨진 링크 고치기, 검사기가 잡은 단순한 위반 고치기.

**처리**

1. 이슈 줄을 `[ ]`로 등록하고, 아래에 `  - 경량: <결과 한 줄>` 줄을 둔다. 결과는 무엇을 어떻게 고쳤는지 한 문장으로 적는다.
2. 작업을 하고 [검증 도구](VerificationTools.md)를 통과시킨다.
3. 이슈 줄을 `[x]`로 바꾸고 `  - 완료일: <날짜>` 줄을 덧붙인다.

경량 이슈는 `[~]` 상태를 쓰지 않고, 진행 중·완료 기록과 연결 작업을 두지 않는다. 작업 중에 조건을 벗어나면(판단이 필요해지거나 범위가 커지면) `경량` 줄을 지우고 [4.1 시작](#41-시작)부터 일반 경로로 처리한다.

### 4.7 완료 기록 보관

완료 문서가 끝없이 커지지 않도록, 마일스톤이 닫히면 그 기록을 보관 문서로 옮긴다.

- 마일스톤의 태스크가 모두 `[x]`가 되면 그 마일스톤이 닫힌다. 마지막 태스크를 완료 처리하는 작업 안에서 보관한다.
- 보관 문서는 `docs/Done-M<n>.md`이다. 완료 문서와 같은 디렉터리에 두어, 기록 안의 상대 링크가 옮긴 뒤에도 그대로 맞게 한다. 그래서 기록을 한 글자도 고치지 않고 옮길 수 있다. 첫 줄은 `# 완료 보관 M<n> <마일스톤 이름>`이고, 그 다음 문단에 목적과 [완료](Done.md)로 돌아가는 링크를 적는다. 기록 형식과 순서는 완료 문서와 같다.
- 그 마일스톤 태스크의 완료 기록과, 그때 완료 문서에 있는 이슈의 완료 기록을 모두 옮긴다. 다른 마일스톤 태스크의 기록은 남긴다.
- [완료](Done.md)의 머리말 문단에 보관 문서 링크를 덧붙인다.
- 옮길 때는 [4.5 기록 보존](#45-기록-보존)대로 줄을 고치거나 빼지 않는다.

## 5. 기록 형식

진행 중과 완료 문서의 항목은 아래 형식을 따른다. 완료 문서에서는 `완료일`, `결과`, `검증`을 반드시 채운다.

```markdown
## M2-T2 초기화 명령 구현

- 시작일: 2026-11-01
- 완료일: 2026-11-02
- 근거 문서: [템플릿 설계](design/Templates.md)
- 관련 이슈: I3

### 계획
- 할 일을 단계별로 적는다.

### 진행 기록
- 2026-11-01: 한 일, 막힌 점, 판단 근거.

### 결정 사항
- 작업 중 내린 결정과 이유. 문서에 반영한 경우 그 문서를 링크한다.

### 변경 파일
- `src/projinit/init.py`

### 결과
- 끝난 상태에서 무엇이 가능해졌는지.

### 검증
- 실행한 검증 명령과 결과.
```

## 6. 문서 형식

[작업 관리 검사기](VerificationTools.md#6-작업-관리-검사기)가 아래 형식을 해석한다. 코드 블록 안의 내용은 해석하지 않는다.

### 6.1 로드맵

- 마일스톤 제목은 `## M<n> <이름>`이다. 마일스톤 번호는 0부터 빠짐없이 차례로 늘어난다.
- 태스크 줄은 `- [<상태>] M<n>-T<m> <한 줄 설명>`이며, 같은 번호의 마일스톤 제목 아래에 둔다. 태스크 번호는 마일스톤마다 1부터 빠짐없이 차례로 늘어난다.
- `- [`로 시작하는 줄이 이 형식에 맞지 않으면 오류다.

### 6.2 이슈

- 이슈 줄은 들여쓰지 않은 `- [<상태>] <I 또는 H><n> <제목>`이다. 번호는 접두어(`I`, `H`)마다 1부터 빠짐없이 차례로 늘어난다.
- 이슈 줄 아래의 들여쓴 `  - <필드>: <값>` 줄은 이슈의 세부 사항이다. 다음 필드는 검사기가 해석한다.
  - `연결 작업: <작업 ID>`: [4.4 취소와 이관](#44-취소와-이관)의 연결.
  - `경량: <결과 한 줄>`: [4.6 가벼운 작업 경로](#46-가벼운-작업-경로)의 경량 이슈 표시. 값이 비면 안 된다.
  - `완료일: <YYYY-MM-DD>`: 경량 이슈가 끝난 날. `[x]`인 경량 이슈에는 있어야 한다.
- 경량 이슈는 `[~]`이면 안 되고, 진행 중·완료 기록과 연결 작업이 없어야 한다.

### 6.3 진행 중·완료 기록

- 기록 하나는 `## <작업 ID> <제목>`으로 시작한다. 두 문서에서 이 수준(`##`)의 제목은 기록 제목으로만 쓴다.
- 기록 제목 바로 아래의 `- <필드>: <값>` 줄이 필드다. 날짜 필드는 `YYYY-MM-DD` 형식이다.
- `### <이름>` 제목이 절이다.
- 진행 중 기록에는 `시작일` 필드와 `계획` 절이 있어야 한다.
- 완료 기록에는 `시작일`, `완료일` 필드와 `계획`, `진행 기록`, `결정 사항`, `변경 파일`, `결과`, `검증` 절이 있어야 한다. 적을 내용이 없는 절에는 `- 없음`을 적는다. 완료 기록은 `완료일`이 늦은 것부터 차례로 놓는다.
- 진행 중 기록이 하나도 없으면 진행 중 문서 본문에 `없음` 한 줄만 둔다.

### 6.4 ID 참조

작업 관리 문서 네 개의 본문(코드 블록과 인라인 코드 제외)에 적힌 작업 ID는 모두 로드맵이나 이슈에 있는 ID여야 한다.

### 6.5 기록 보존 검사

[4.5 기록 보존](#45-기록-보존)을 git의 마지막 커밋(`HEAD`)과 비교해 검사한다.

- 비교 단위는 기록 안의 줄이다. 빈 줄과 코드 블록 안의 줄은 비교하지 않고, 줄 끝 공백은 무시한다. 줄의 순서와 어느 절에 있는지는 비교하지 않는다.
- `HEAD`의 진행 중 기록이 지금도 진행 중에 있으면, 그 기록의 `진행 기록`·`결정 사항` 절의 줄이 지금 기록에 모두 있어야 한다.
- `HEAD`의 진행 중 기록이 진행 중에서 사라졌으면, 같은 ID의 완료 기록이 있어야 하고 `HEAD` 기록의 모든 줄이 그 안에 있어야 한다.
- `HEAD`의 완료 기록(완료 문서와 보관 문서)은 지금도 완료 문서나 보관 문서 중 하나에 있어야 하고, 모든 줄이 그대로 있어야 한다.
- git 저장소가 아니거나 `HEAD`에 해당 문서가 없으면 이 검사를 건너뛴다.

### 6.6 완료 보관

- 완료 기록은 완료 문서와 보관 문서(`docs/Done-M*.md`)를 합쳐서 본다. 같은 ID의 기록이 두 곳 이상에 있으면 안 된다.
- 보관 문서의 이름은 `Done-M<n>.md`이고(`<n>`은 숫자), 마일스톤 n이 로드맵에 있고 닫혀 있어야 한다.
- 닫힌 마일스톤 태스크의 완료 기록은 그 마일스톤의 보관 문서에 있어야 한다.
- 보관 문서에 있는 태스크 기록은 그 문서의 마일스톤 태스크여야 한다. 이슈 기록은 어느 보관 문서에 있어도 된다.
- 보관 문서마다 [6.3](#63-진행-중완료-기록)의 완료 기록 규칙(필수 필드·절, 순서)을 적용한다.

### 6.7 커밋 메시지

커밋 하나하나가 어느 작업의 것인지 알 수 있도록, 커밋 메시지의 첫 줄(제목)은 작업 ID로 시작한다.

```text
<작업 ID>[, <작업 ID>...][(진행 중)]: <요약>
```

- 작업 ID는 [로드맵](Roadmap.md)이나 [이슈](Issue.md)에 있어야 한다. 커밋 하나가 여러 작업을 담으면 `, `로 이어 적는다.
- 작업이 끝나지 않은 상태의 커밋(진행 중 기록, 목업)은 ID 바로 뒤에 `(진행 중)`을 붙인다.
- 요약은 `: ` 뒤에 한 줄로 적는다. 본문은 빈 줄 다음에 자유롭게 적는다.
- git이 만드는 제목(`Merge `, `Revert `, `fixup! `, `squash! `로 시작)은 이 형식을 따르지 않아도 된다.
- 예: `M0-T6: 커밋 메시지와 작업 ID 연결`, `M0-T8, I1: 언어 독립 포인터 검사`, `I3(진행 중): 기록 보존 검사 목업`

이 형식은 git `commit-msg` hook이 [커밋 메시지 검사기](VerificationTools.md#10-커밋-메시지-검사기)로 검사한다.

## 7. 검증

작업을 시작하거나 끝낼 때, 작업 관리 문서를 고칠 때마다 [작업 관리 검사기](VerificationTools.md#6-작업-관리-검사기)를 실행한다.

```sh
uv run python -m tools.check_tasks
```
