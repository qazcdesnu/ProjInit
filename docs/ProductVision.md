# 제품 비전

이 문서는 ProjInit이 무엇을 만들고 왜 만드는지 정한다. 모든 제품 기능 문서와 제품 코드는 이 문서를 근거로 한다. 전체 문서 목록은 [문서 인덱스](index.md)에서 확인한다.

## 1. 목적

ProjInit은 Claude Code로 하는 모든 프로젝트를 **문서와 코드 두 축**의 같은 규칙 체계로 시작하고 유지하게 하는 CLI다. 어떤 프로젝트에서든 같은 방식으로 작업하는 일관된 코딩 경험을 주는 것이 목적이다.

규칙 체계의 핵심은 다음과 같다. 각 규칙의 상세는 이 저장소 자신이 따르는 규칙 문서에 있다.

- **문서 우선**: 문서가 코드의 규칙이며, 문서를 먼저 쓰고 그 지시에 따라 코드를 쓴다([문서 작업 규칙](DocumentationRule.md#1-문서-우선-원칙)).
- **하나의 진입점**: `CLAUDE.md` → [문서 인덱스](index.md) → 작업별 문서 순서로 읽으며, 고아 문서가 없다.
- **양방향 추적**: 문서는 AST 심볼 이름으로 코드를 가리키고, 코드는 `@doc:`로 근거 문서를 가리킨다([포인터 규약](Traceability.md)).
- **작업 ID**: 모든 작업은 `M<n>-T<m>`, `I<n>`, `H<n>` ID로 로드맵·이슈·진행 중·완료 문서에 기록된다([작업 관리 규칙](TaskRule.md)).
- **검사기 동반**: 기계적으로 검사할 수 있는 규칙은 검사기로 검증한다([검증 도구](VerificationTools.md)).

## 2. 출발점

이 체계는 AgentVis 프로젝트(`/Users/qazcde/Desktop/Playground/AgentVis`, Claude Code 작업 과정 시각화)에서 처음 만들어졌다. 2026-10-31에 AgentVis의 공통 규칙 문서, 검사기(`tools/`), 검사기 테스트를 이 저장소로 복사해 출발점으로 삼았다. 이 저장소는 그 규칙을 스스로 따르며 개발한다.

AgentVis는 ProjInit의 첫 번째 사용 프로젝트가 된다. ProjInit이 준비되면 AgentVis의 `tools/`와 공통 규칙 문서를 ProjInit이 관리하도록 전환한다.

## 3. 핵심 요구사항

1. **초기화**: 새 프로젝트(또는 기존 디렉터리)에 규칙 체계를 만든다.
2. **유지**: 규칙 템플릿과 검사기가 바뀌면, 이미 초기화된 프로젝트를 같은 규칙으로 갱신할 수 있어야 한다. 프로젝트마다 복사본이 따로 바뀌어 일관성이 깨지는 것을 막는 것이 이 제품의 가장 중요한 가치다.
3. **강제**: 검사기가 작업자(에이전트)의 기억에 의존하지 않고 자동으로 실행되어야 한다.
4. **분리**: 공통 규칙과 프로젝트 고유 문서(제품 비전, 구조, 상세 설계)를 섞지 않는다. 공통 규칙만 생성·갱신하고, 고유 문서는 빈 자리만 만든다.

## 4. 구성 초안

M0에서 확정한다.

| 구분 | 내용 | 처리 방식 |
| --- | --- | --- |
| 공통 규칙 문서 | `CLAUDE.md`, 문서·코드·포인터·작업 관리 규칙, 검증 도구, 인덱스 | 템플릿으로 생성·갱신 |
| 작업 관리 문서 | 빈 로드맵, 진행 중("없음"), 완료, 이슈 | 처음에만 생성 |
| 검사기 | 문서 링크, 포인터, 작업 관리 검사기 | 프로젝트에 복사하지 않고, 버전을 고정한 개발 의존성으로 설치 |
| 강제 장치 | Claude Code hook(Stop), git pre-commit | 초기화할 때 설치 |
| 프로젝트 고유 문서 | 제품 비전, 시스템 구조, 상세 설계 | 생성하지 않음. 인덱스에 자리만 둠 |

명령 초안: `init`(초기화), `check`(검사 일괄 실행), `upgrade`(규칙 템플릿과 검사기 버전 갱신).

## 5. 출발 시점에 알려진 약점

AgentVis에서 이 체계를 쓰며 드러난 약점이다. 템플릿으로 굳히기 전에 규칙부터 보완한다. 각 항목은 [로드맵](Roadmap.md)의 M0 태스크로 잡혀 있다.

| 약점 | 내용 |
| --- | --- |
| 약한 강제력 | 검사기를 작업자가 직접 실행해야 한다. 실제로 규칙 위반(개인 메모리에 규칙 저장, 시스템 Python 실행)이 사람의 지적으로만 발견되었다. |
| 무거운 절차 | 오타 하나를 고쳐도 이슈 → 진행 중 → 완료를 모두 거쳐야 한다. |
| 끝없이 커지는 완료 문서 | `Done.md`를 나누는 규칙이 없다. |
| 커밋과 작업 ID의 단절 | 커밋 메시지에 작업 ID를 쓰는 규칙과 검사가 없다. |
| 느슨한 상호 참조 | 모듈 docstring의 `@doc:` 하나로 그 파일의 모든 심볼이 상호 참조 검사를 통과한다. |
| Python 전용 포인터 검사 | 다른 언어 프로젝트에서는 포인터 축이 빠진다. |

## 6. 미결정 사항

결정되면 이 절에서 지우고 해당 문서에 반영한다.

- 대상 언어: 처음에는 Python 프로젝트만 대상으로 할지, 다른 언어도 포함할지.
- 강제 방식: Claude Code Stop hook, git pre-commit, 또는 둘 다.
- 배포 방식: git 저장소 주소로 설치할지, 패키지 저장소에 배포할지.
