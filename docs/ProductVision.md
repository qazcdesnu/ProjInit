# 제품 비전

이 문서는 ProjInit이 무엇을 만들고 왜 만드는지 정한다. 모든 제품 기능 문서와 제품 코드는 이 문서를 근거로 한다. 전체 문서 목록은 [문서 인덱스](index.md)에서 확인한다.

## 1. 목적

ProjInit은 **Claude Code 프로젝트 초기화 CLI**다. Claude Code로 하는 모든 프로젝트를 **문서와 코드 두 축**의 같은 규칙 체계로 시작하고 유지하게 한다. 어떤 프로젝트에서든 같은 방식으로 작업하는 일관된 코딩 경험을 주는 것이 목적이다.

최종 사용 흐름은 다음과 같다.

1. 사용자가 빈 폴더(또는 기존 폴더)에서 ProjInit으로 초기화한다.
2. 그 폴더에서 Claude Code를 시작한다.
3. 첫 세션이 시작되면 Claude가 먼저 어떤 개발 프로젝트를 하고 싶은지 물어보고, 대화로 받은 답을 제품 비전과 첫 로드맵으로 정리하며 프로젝트를 시작한다.

사용자는 규칙 체계를 따로 공부하거나 설정하지 않고, 초기화 한 번과 대화만으로 규칙을 따르는 프로젝트를 시작한다.

규칙 체계의 핵심은 다음과 같다. 각 규칙의 상세는 이 저장소 자신이 따르는 규칙 문서에 있다.

- **문서 우선**: 문서가 코드의 규칙이며, 문서를 먼저 쓰고 그 지시에 따라 코드를 쓴다([문서 작업 규칙](DocumentationRule.md#1-문서-우선-원칙)).
- **하나의 진입점**: `CLAUDE.md` → [문서 인덱스](index.md) → 작업별 문서 순서로 읽으며, 고아 문서가 없다.
- **양방향 추적**: 문서는 구문 트리의 심볼 이름으로 코드를 가리키고, 코드는 `@doc:`로 근거 문서를 가리킨다([포인터 규약](Traceability.md)).
- **작업 ID**: 모든 작업은 `M<n>-T<m>`, `I<n>`, `H<n>` ID로 로드맵·이슈·진행 중·완료 문서에 기록된다([작업 관리 규칙](TaskRule.md)).
- **검사기 동반**: 기계적으로 검사할 수 있는 규칙은 검사기로 검증한다([검증 도구](VerificationTools.md)).

## 2. 출발점

이 체계는 AgentVis 프로젝트(`/Users/qazcde/Desktop/Playground/AgentVis`, Claude Code 작업 과정 시각화)에서 처음 만들어졌다. 2026-10-31에 AgentVis의 공통 규칙 문서, 검사기(`tools/`), 검사기 테스트를 이 저장소로 복사해 출발점으로 삼았다. 이 저장소는 그 규칙을 스스로 따르며 개발한다.

AgentVis는 ProjInit으로 전환하지 않는다. 실제로 쓰이며 잘 돌아가는 프로젝트라 함부로 바꾸지 않기로 했다(I17). AgentVis의 규칙이 바뀌면, ProjInit에 필요한 것만 골라 이슈로 반영한다(예: I12의 커밋 규칙과 PR 규칙). ProjInit으로 처음부터 만든 첫 프로젝트는 `Jjabtero`다.

## 3. 핵심 요구사항

1. **초기화**: 새 프로젝트(또는 기존 디렉터리)에 규칙 체계를 만든다. 이것이 이 제품의 중심 기능이며, 먼저 만든다.
2. **기능은 차차 넣는다**: 초기화 말고 사용자가 쓰는 기능(이미 초기화된 프로젝트의 갱신, 참고 프로젝트를 보고 초기화하기 등)은 초기화가 완성된 뒤 하나씩 정해서 넣는다. 후보는 [7. 이후 기능 후보](#7-이후-기능-후보)에 둔다.
3. **강제**: 검사기가 작업자(에이전트)의 기억에 의존하지 않고 자동으로 실행되어야 한다.
4. **분리**: 공통 규칙과 프로젝트 고유 문서(제품 비전, 구조, 상세 설계)를 섞지 않는다. 공통 규칙만 생성·갱신하고, 고유 문서는 빈 자리만 만든다.
5. **개발 언어 독립**: 문서 관리 도구(검사기·검증기)는 uv 환경의 Python으로 만들지만, 대상 프로젝트의 개발 코드 언어는 Python일 필요가 없다. 문서와 코드는 포인터로만 연결되며, 코드는 문서의 계약대로 작성되고 코드의 근거는 문서에서 찾는다. 이 연결은 어떤 개발 언어에서도 같은 방식으로 동작해야 한다.
6. **첫 세션 시작 안내**: 초기화한 폴더에서 Claude Code를 열고 `/start`를 입력하면, Claude가 만들 프로젝트를 물어보며 첫 작업을 시작한다. 답을 받아 프로젝트 고유 문서(제품 비전, 시스템 구조)와 첫 로드맵을 채운다. 초기화는 마지막에 이 사용법을 알려 준다. Claude Code는 사용자가 입력하기 전에 Claude가 먼저 말하게 하는 기능이 없어서(SessionStart hook은 맥락만 넣는다), 사용자가 명령 하나로 시작하게 한다.
7. **자기 적용과 되먹임**: ProjInit은 자신이 만드는 규칙 체계(문서·코드 두 축) 안에서 개발한다. 작업 중에 두 축이 맞물리는 구조의 개선점을 발견하면, 이 저장소의 규칙·검사기와 제품이 배포하는 템플릿·검사기 양쪽에 반영한다.
   - 두 곳이 따로 바뀌지 않도록 공통 규칙과 검사기의 원본은 하나만 둔다. 이 저장소의 공통 규칙 문서와 `projinit` 패키지(`src/projinit/`)가 곧 제품이 배포하는 원본이다.
   - 이 저장소도 ProjInit으로 초기화된 다른 프로젝트와 같은 검사기와 같은 강제 장치로 검사한다.
   - 개선점은 [이슈](Issue.md)로 등록하고, 규칙을 먼저 고친 뒤 검사기를 고친다. 예: M0-T8은 이 저장소에서 Python 전용 포인터 규약의 한계를 발견해 언어 독립 규약으로 바꾼 것이다.

## 4. 구성 초안

큰 방향은 M0-T2에서 정했다. 검사기 패키지와 설정 형식은 [패키지 구성 설계](design/Package.md)에, 초기화가 만드는 파일은 [템플릿 구성 설계](design/Templates.md)에 있다.

| 구분 | 내용 | 처리 방식 |
| --- | --- | --- |
| 공통 규칙 문서 | `CLAUDE.md`, 문서·코드·포인터·작업 관리 규칙, 커밋 규칙, PR 규칙, 검증 도구, 인덱스 | 초기화할 때 템플릿으로 생성. 템플릿의 원본은 이 저장소 자신의 공통 규칙 문서다. |
| 작업 관리 문서 | 빈 로드맵, 진행 중("없음"), 완료, 이슈 | 처음에만 생성 |
| 검사기 | 문서 링크, 포인터, 작업 관리 검사기 | 프로젝트에 복사하지도, 의존성으로 설치하지도 않는다. 대상 프로젝트는 설정 파일에 ProjInit 버전만 고정하고, `uvx`로 그 버전을 받아 실행한다. 그래서 개발 언어와 무관하며, Python이 아닌 프로젝트에 `pyproject.toml`을 만들지 않는다. |
| 강제 장치 | Claude Code Stop hook, git pre-commit, git commit-msg | 초기화할 때 설치. Stop hook은 Claude가 턴을 끝내기 전에 검사하고, 실패 내용을 Claude에게 돌려줘 스스로 고치게 한다. pre-commit은 사람의 커밋을 포함한 모든 커밋을 검사해 실패하면 거부한다. |
| CI와 PR 템플릿 | GitHub Actions 워크플로(일괄 검사, PR 제목·브랜치·순서 검사), PR 본문 템플릿 | 초기화할 때 설치. 커밋 규칙과 PR 규칙은 AgentVis에서 ProjInit을 분리한 뒤 공통 규칙 체계에 추가된 것으로, 이 저장소가 먼저 따르고(I12) 초기화가 만드는 템플릿에도 들어간다. 원격 저장소 주소처럼 프로젝트마다 다른 부분은 M2-T1에서 템플릿의 빈 자리로 정한다. |
| 프로젝트 고유 문서 | 제품 비전, 시스템 구조, 상세 설계 | 생성하지 않음. 인덱스에 자리만 둠 |
| 첫 세션 안내 | 프로젝트 슬래시 명령 `/start`(`.claude/commands/start.md`)와 작업 관리 규칙의 첫 작업 절차 | 초기화할 때 설치 |

명령: 사용자가 쓰는 명령은 `init`(초기화)과 `upgrade`(새 버전으로 갱신) 둘이다. `check`(검사 일괄 실행)와 `commit-msg`(커밋 메시지 검사)는 초기화된 프로젝트의 hook이 검사기를 실행하기 위한 부품이며, 사람이 직접 칠 일은 거의 없다.

배포: ProjInit은 git 저장소의 태그(`v0.1.0` 등)로 버전을 구분해 배포한다. 실행 예는 `uvx --from git+<저장소 주소>@<태그> projinit check`이며, 사람이 아니라 hook이 실행한다. 패키지 저장소(PyPI) 배포는 하지 않으며, 필요해지면 그때 다시 정한다.

## 5. 출발 시점에 알려진 약점

AgentVis에서 이 체계를 쓰며 드러난 약점이다. 템플릿으로 굳히기 전에 규칙부터 보완한다. 각 항목은 [로드맵](Roadmap.md)의 M0 태스크로 잡혀 있다.

| 약점 | 내용 |
| --- | --- |
| 약한 강제력 | 검사기를 작업자가 직접 실행해야 한다. 실제로 규칙 위반(개인 메모리에 규칙 저장, 시스템 Python 실행)이 사람의 지적으로만 발견되었다. |
| 무거운 절차 | 오타 하나를 고쳐도 이슈 → 진행 중 → 완료를 모두 거쳐야 한다. |
| 끝없이 커지는 완료 문서 | `Done.md`를 나누는 규칙이 없다. |
| 커밋과 작업 ID의 단절 | 커밋 메시지에 작업 ID를 쓰는 규칙과 검사가 없다. |
| 느슨한 상호 참조 | 모듈 docstring의 `@doc:` 하나로 그 파일의 모든 심볼이 상호 참조 검사를 통과한다. |
| Python 전용 포인터 검사 | 포인터 규약이 Python AST에 묶여 있어 다른 언어 프로젝트에서는 포인터 축이 빠진다. [3. 핵심 요구사항](#3-핵심-요구사항)의 개발 언어 독립과 충돌한다. |

## 7. 이후 기능 후보

초기화가 완성된 뒤 하나씩 정해서 넣을 기능이다. 아직 로드맵 태스크가 아니며, 넣기로 정하면 로드맵에 마일스톤을 만든다.

- **참고 프로젝트로 초기화**: 이미 진행된 프로젝트를 `proto/` 폴더에 넣으면, 그 프로젝트를 보고 초기화한다(예: 제품 비전과 첫 로드맵의 초안을 그 프로젝트에서 뽑는다).
- **갱신**: 규칙 템플릿과 검사기가 바뀌었을 때 이미 초기화된 프로젝트를 새 규칙으로 갱신한다(이전 계획의 `upgrade`, M3). 실제로 써 보며 필요해져 M5로 넣었다(I16).
