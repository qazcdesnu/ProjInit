# 완료 보관 M7 테스트 체계

이 문서는 닫힌 마일스톤 M7의 완료 기록을 보관한다. 기록 형식은 [작업 관리 규칙](TaskRule.md#5-기록-형식)을 따르며, 아직 닫히지 않은 마일스톤의 기록은 [완료](Done.md)에 있다.

## M7-T3 시나리오 테스트와 0.2.0 릴리스

- 시작일: 2026-11-01
- 완료일: 2026-11-01
- 근거 문서: [시스템 구조](Architecture.md#3-테스트), [검사기 설계의 시나리오 테스트](design/Checkers.md#51-시나리오-테스트)
- 참고 자료: 없음

### 계획
- 전수조사(M7-T1 기록)를 `tests/scenario/`의 영구 테스트로 옮긴다. 지금 코드로 기준 프로젝트를 한 번 만들고, 경우마다 복사해 규칙 하나를 깨뜨린 뒤 담당 검사기가 맞는 메시지로 잡는지 본다. 통과해야 하는 경우도 둔다.
- 빠르게: 검사기는 같은 프로세스에서 부르고, 실제 git hook·Stop hook·하위 명령만 명령으로 실행한다.
- 버전을 `0.2.0`으로 올린다.

### 진행 기록
- 2026-11-01: 사용자가 진행하라고 했다.
- 2026-11-01: 설계 문서에 `init_project`와 `refresh_common`을 코드 포인터로 걸었더니 그 함수들에 이 설계 문서로 가는 역방향 포인터를 요구했다. 그 함수의 근거는 템플릿 구성 설계이므로, 초기화 명령 절을 링크하고 함수 이름은 인라인 코드로 적었다.
- 2026-11-01: `tests/scenario/`에 공통 도구와 규칙 영역별 시나리오 6개 파일(97개 테스트)을 만들었다. 같은 프로세스에서 검사기를 불러 25초 안에 돈다. 일괄 검사 전체는 약 32초다.
- 2026-11-01: 시나리오 하나가 PR 제목 메시지의 조사 오류("(진행 중)를")를 드러냈다. "(진행 중)을"로 고치고 단위 테스트도 고쳤다.
- 2026-11-01: 시나리오가 검사기 고장을 잡는지 확인했다. `check_links`가 늘 빈 목록을 돌려주게 일부러 고치자 링크 관련 시나리오 8개가 정확히 실패했고, 되돌렸다.

### 결정 사항
- 시나리오의 `projinit`은 배포된 태그가 아니라 지금 코드다(`<python> -m projinit.cli`). 그래서 버전 일치 검사는 시나리오에서 빠지고 단위 테스트가 본다. 같은 이유로 갱신 명령의 거부도 단위 테스트가 본다.
- 일괄 검사가 약 6초에서 32초로 늘었다. Stop hook의 시간 제한(180초) 안이고 턴마다 도는 비용으로 받아들일 만하다. 더 느려지면 병렬 실행을 먼저 검토한다([코드 작업 규칙의 실행](CodeRule.md#53-실행)).
- 버전을 `0.2.0`으로 올린다. 자료 폴더 체계, 세션 시작 안내, 테스트 체계가 들어간 단계다.

### 변경 파일
- `docs/Roadmap.md`, `docs/Ongoing.md`, `docs/Done.md`, `docs/Done-M7.md`(M7이 닫혀 M7 기록을 옮김)
- `tests/scenario/__init__.py`, `tests/scenario/project.py`, `tests/scenario/test_doc_rules.py`, `test_pointer_rules.py`, `test_task_rules.py`, `test_material_rules.py`, `test_device_rules.py`, `test_commit_rules.py`
- `src/projinit/check_commits.py`, `tests/unit/test_check_commits.py`
- `docs/Architecture.md`, `docs/design/Checkers.md`
- `README.md`, `pyproject.toml`, `uv.lock`

### 결과
- 검사기를 일부러 깨뜨려 확인하는 시나리오 97개가 영구 테스트로 있고, 일괄 검사가 매번 실행한다. 검사기가 무조건 통과하게 바뀌면 바로 드러난다.
- 버전 `0.2.0`. 병합 뒤 `v0.2.0` 태그를 붙인다.

### 검증
- `uv run projinit check`: 모두 통과
- `check_links`를 일부러 고장 내면 링크 시나리오 8개가 실패함을 확인

## M7-T2 대소문자만 다른 링크를 로컬에서도 잡는 검사

- 시작일: 2026-11-01
- 완료일: 2026-11-01
- 근거 문서: [문서 작업 규칙](DocumentationRule.md#3-링크-규칙), [검증 도구](VerificationTools.md#3-문서-링크-검사기)
- 참고 자료: 없음

### 계획
- 링크 경로와 `@doc:` 경로는 대소문자까지 실제 파일 이름과 같아야 한다는 규칙을 문서 작업 규칙과 포인터 규약에 적는다.
- 공통 모듈에 실제 대소문자 경로를 찾는 함수를 두고, 문서 링크 검사기(코드 포인터 포함)와 포인터 검사기의 `@doc:` 검사가 쓴다.
- 대소문자를 구분하지 않는 파일 시스템(macOS 기본)에서도 Stop hook과 pre-commit이 잡는다. CI 절의 설명을 고친다.

### 진행 기록
- 2026-11-01: 전수조사에서 대소문자만 다른 링크가 macOS에서는 통과하고 CI에서만 잡히는 것을 확인했다(M7-T1 기록). 사용자가 검토한 대로 진행하라고 했다.
- 2026-11-01: `actual_case`를 구현해 `check_links`와 `check_doc_pointers`가 쓰게 했다. 전수조사의 D14 경우(대소문자만 다른 링크)를 지금 코드로 다시 돌리자 `링크 대상의 대소문자가 다름`으로 잡혔다.

### 결정 사항
- 디렉터리 목록으로 각 경로 부분을 비교한다. 대소문자를 구분하지 않는 파일 시스템에서는 `exists()`가 참이 되어 존재 검사로는 알 수 없다.
- 테스트는 파일 시스템에 따라 갈린다. 구분하지 않는 곳에서는 대소문자 메시지를, 구분하는 곳(CI)에서는 기존의 대상 없음 메시지를 기대한다. 어느 쪽이든 잡히는지를 본다.

### 변경 파일
- `docs/Roadmap.md`, `docs/Ongoing.md`, `docs/Done.md`
- 템플릿: `src/projinit/templates/docs/DocumentationRule.md`, `Traceability.md`, `VerificationTools.md`, 그리고 다시 만든 이 저장소의 같은 문서
- `src/projinit/doclib.py`, `src/projinit/check_docs.py`, `src/projinit/check_pointers.py`, `docs/design/Checkers.md`
- `tests/unit/test_doclib.py`, `tests/unit/test_check_docs.py`, `tests/unit/test_check_pointers.py`

### 결과
- 대소문자만 다른 문서 링크, 코드 포인터, `@doc:` 경로를 macOS에서도 Stop hook과 pre-commit이 잡는다.

### 검증
- `uv run projinit check`: 모두 통과
- 전수조사 D14 경우: 지금 코드로 잡힘

## M7-T1 테스트 종류와 배치의 공통 규칙

- 시작일: 2026-11-01
- 완료일: 2026-11-01
- 근거 문서: [코드 작업 규칙](CodeRule.md#5-테스트), [시스템 구조](Architecture.md#3-테스트)
- 참고 자료: 없음

### 계획
- 코드 작업 규칙 5절에 테스트 종류(단위, 통합, 종단)와 배치 원칙(종류마다 최상위 폴더, 그 안은 코드 구조를 따름, 언어 관례가 다르면 그 관례)을 더한다. 버그를 고칠 때는 재현 테스트를 먼저 더한다. 구체적인 폴더 이름과 명령은 시스템 구조가 정한다.
- 작업 관리 규칙 4.8절: 첫 작업이 시스템 구조에 테스트 종류와 폴더를 정한다.
- 이 저장소: 지금의 테스트를 `tests/unit/`으로 옮기고 시스템 구조 3절과 설계 문서의 링크를 고친다. 시나리오 테스트(`tests/scenario/`)는 M7-T3에서 만든다.

### 진행 기록
- 2026-11-01: 사용자가 검사기를 일부러 깨뜨려 작동하는지 전수조사하자고 했다. 배포된 `v0.1.10`으로 임시 프로젝트를 만들어 111개 경우를 시험했고, 검사기가 놓친 경우는 없었다(대소문자만 다른 링크는 macOS에서 통과하고 CI에서 잡히는 알려진 한계). 이어 사용자가 테스트 코드가 영역별로 체계적으로 관리되고 있는지 물었고, 공통 규칙에 테스트 종류와 배치가 없고 전수조사가 저장소에 남지 않는다고 답했다. 테스트 종류 규칙, 종류별 폴더, 시나리오 테스트, 대소문자 검사를 M7로 넣고 0.2.0으로 올리기로 했다.
- 2026-11-01: 코드 작업 규칙 5절에 5.1 테스트 종류, 5.2 배치, 5.3 실행을 더하고, 작업 관리 규칙 4.8절의 시스템 구조 작성에 테스트 종류와 폴더를 넣었다. 테스트 21개를 `tests/unit/`으로 옮기고, 저장소 루트를 찾던 `test_release.py`의 경로와 설계 문서의 테스트 링크를 고쳤다.

### 결정 사항
- 공통 규칙은 원칙(종류마다 폴더, 그 안은 코드 구조, 언어 관례 우선)만 정하고, 실제 폴더 이름과 명령은 시스템 구조가 정한다. 언어마다 관례가 달라서다.
- 일괄 검사는 턴마다 돌므로 테스트는 빨라야 한다. 느린 종류를 CI에서만 돌리는 것은 시스템 구조에 적는 결정으로만 허용한다.

### 변경 파일
- `docs/Roadmap.md`, `docs/Ongoing.md`, `docs/Done.md`
- 템플릿: `src/projinit/templates/docs/CodeRule.md`, `TaskRule.md`, 그리고 다시 만든 이 저장소의 같은 문서
- `docs/Architecture.md`, `docs/design/Checkers.md`, `docs/design/Templates.md`
- `tests/test_*.py` → `tests/unit/test_*.py`, `tests/unit/__init__.py`

### 결과
- 공통 규칙이 테스트 종류(단위, 통합, 종단), 배치, 실행을 정한다. 첫 작업이 시스템 구조에 테스트 종류와 폴더를 정한다.
- 이 저장소의 테스트는 `tests/unit/`에 있다. 시나리오 테스트는 M7-T3에서 `tests/scenario/`에 둔다.

### 검증
- `uv run projinit check`: 모두 통과
