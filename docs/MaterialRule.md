# 자료 폴더 규칙

이 문서는 프로젝트 밖에서 가져온 자료를 두는 세 폴더, 참고 자료 폴더 `reference/`, 기존 프로젝트 폴더 `legacy/`, 로컬 자료 폴더 `private/`의 규칙을 정한다. 세 폴더는 문서도 코드도 아니며, 자료의 성격이 달라 따로 둔다. 전체 문서 목록은 [문서 인덱스](index.md)에서 확인한다.

## 1. 세 폴더

| 폴더 | 두는 것 | 성격 | 목록 문서 |
| --- | --- | --- | --- |
| `reference/` | 개발하면서 계속 참고하는 자료: 명세, 논문, 외부 API 문서, 디자인 시안, 샘플 데이터 등 | 살아 있는 자료. 개발 중에 더하고 고치고 지운다. | `docs/Reference.md` (선택) |
| `legacy/` | ProjInit 없이 작업하던 기존 개발 프로젝트 | 아카이브. 넣은 뒤로는 고치지 않는다. | `docs/Legacy.md` |
| `private/` | 저장소에 올리면 안 되는 자료: 계약서, 내부 문서, 고객 데이터 샘플 등 | 로컬 전용. 커밋하지 않고, 어떤 문서도 링크하지 않는다. | 두지 않는다 |

- 세 폴더는 필요할 때 만든다. 초기화는 만들지 않는다.
- 폴더 위치는 [설정](VerificationTools.md#11-설정)의 `paths.reference`, `paths.legacy`, `paths.private`로 바꿀 수 있다. 목록 문서의 이름은 바꾸지 않는다.
- 자료 폴더는 코드 루트가 아니다. 제품 코드는 자료 폴더의 파일을 불러오거나 실행하지 않는다. 자료의 코드나 데이터가 제품에 필요하면 코드 루트에 새로 만들고, 그 근거로 자료를 문서에서 링크한다.
- `reference/`와 `legacy/`에는 비밀 정보(키, 비밀번호, 개인 정보)를 넣지 않는다. 저장소에 올리면 안 되는 자료는 `private/`에 넣는다. 내려받을 수 있는 큰 자료는 파일을 넣지 않고 목록 문서에 출처만 적어도 된다.
- 규칙이 정한 이름은 목록 문서뿐이다. 자료 폴더 안의 구성은 자유다.

## 2. 목록 문서

자료 폴더의 파일은 문서가 아니라서 [문서 인덱스](index.md)에서 링크를 따라 찾을 수 없다. 그래서 폴더마다 목록 문서를 두고 자료가 무엇이고 어디에 쓰는지 적는다.

- 목록 문서는 [참고 자료 목록](Reference.md "선택")과 [기존 프로젝트 목록](Legacy.md "선택")이다. 이 규칙이 [선택 링크](DocumentationRule.md#3-링크-규칙)로 가리키므로, 만들기만 하면 인덱스에서 도달한다. 인덱스에 따로 링크를 더하지 않아도 된다.
- `legacy/`에 파일이 하나라도 있으면 기존 프로젝트 목록이 있어야 하고, 목록은 폴더의 모든 파일을 링크한다. 폴더를 링크하면 그 아래 모든 파일을 링크한 것으로 본다. 기존 프로젝트는 폴더 하나를 링크한다.
- 참고 자료 목록은 없어도 되고, 모든 자료를 올리지 않아도 된다. 참고 자료는 쓸 수도 안 쓸 수도 있어, 넣을 때마다 목록을 강제하지 않는다. 목록에 올리지 않은 자료도 [세션 시작 안내](#6-세션-시작-안내)로 에이전트가 안다. 어디에 쓰는지 알게 된 자료부터 목록에 올린다.
- 항목마다 무엇인지, 어디에 쓰는지(관련 기능이나 결정), 출처(주소나 받은 곳), 넣은 날짜를 적는다. 긴 자료는 자주 보는 쪽이나 절도 적는다.

```markdown
- [결제 API 명세](../reference/payment-api.pdf): 결제 대행사의 REST API 명세. 쓰는 곳: 결제 기능 설계, 특히 4장 웹훅. 출처: https://example.com/docs. 넣은 날짜: 2026-11-01.
- 경쟁 서비스 가격표: 가격 정책을 정할 때 비교한다. 파일 없이 출처만 둔다. 출처: https://example.com/pricing. 넣은 날짜: 2026-11-01.
```

- 자료 폴더 안 코드 파일 링크는 [포인터 규약](Traceability.md)의 코드 포인터가 아니다. 파일이 있는지만 검사한다.

## 3. 참고 자료 폴더 `reference/`

### 3.1 넣는 것

개발에 앞서 조사한 자료와 개발 중에 생기는 자료를 넣는다.

- 조사 메모와 정리 노트. 사용자가 직접 쓴 메모나 아이디어 정리도 자료다.
- 명세, 표준, 논문, 보고서, 외부 API 문서
- 디자인 시안, 화면 캡처, 다이어그램
- 샘플 데이터, 참고할 예제 코드
- 공개 저장소라면 공개해도 되는 자료만 넣는다. 자료는 저장소에 커밋된다. 공개할 수 없는 자료는 파일 없이 목록 문서에 무엇이고 어디서 볼 수 있는지만 적는다.

### 3.2 형식

에이전트가 바로 읽을 수 있는 형식으로 넣는다.

- 바로 읽는 형식: 텍스트, 마크다운, CSV, JSON, 코드 같은 텍스트 파일, PDF, 이미지(PNG, JPG 등).
- 워드, 엑셀, 파워포인트, 한글 같은 문서 파일은 PDF나 마크다운, CSV로 바꿔 넣는다. 원본도 남기려면 함께 넣고, 목록 문서에서 변환본을 읽으라고 적는다.
- 웹 페이지는 PDF나 마크다운으로 저장해 넣는다. 자주 바뀌는 페이지는 파일 없이 목록 문서에 주소만 적고, 작업할 때 그 주소를 읽는다.
- 파일 이름은 내용이 드러나게 짓는다. 자료가 많으면 주제별 하위 폴더(예: `reference/api/`, `reference/design/`)로 나눈다.

### 3.3 넣는 방법

- 사용자는 파일을 폴더에 넣기만 하면 된다. 목록 문서는 에이전트가 쓴다. 사용자가 무엇이고 어디에 쓸지 알려 주면 그대로 적고, 알려 주지 않으면 그 자료를 쓰게 될 때 읽고 짐작한 내용을 사용자에게 확인한 뒤 적는다.
- 프로젝트를 시작하기 전에 모은 자료는 초기화 전이나 후에 넣고 `/start`로 시작한다. 첫 작업이 자료를 먼저 읽는다([작업 관리 규칙의 첫 작업](TaskRule.md#48-첫-작업)).
- 개발 중에 넣은 자료는 목록에 올리지 않아도 커밋할 수 있다. 커밋 메시지에는 다른 커밋처럼 작업 ID가 필요하므로, 에이전트에게 맡기거나 이슈 ID로 커밋한다([커밋 규칙](CommitRule.md#3-메시지-형식)).

### 3.4 쓰는 방법

- 작업을 시작할 때 [세션 시작 안내](#6-세션-시작-안내)와 목록 문서에서 그 작업과 관련된 자료를 찾아 읽고, 진행 중 기록의 `참고 자료` 줄에 적는다([작업 관리 규칙의 시작](TaskRule.md#41-시작)). 관련 자료가 없으면 "없음"으로 적는다. 긴 자료는 목록에 적힌 쪽이나 절부터 필요한 부분만 읽는다.
- 목록에 없던 자료를 작업에 쓰면, 그 작업에서 목록에 올린다.
- 자료는 근거이고, 결정은 문서에 둔다. 자료에서 가져와 정한 것(요구사항, 데이터 형식, API 규약, 수치)은 제품 비전이나 설계 문서에 옮겨 적고 근거로 그 자료를 링크한다. 코드는 자료가 아니라 그 문서를 근거로 한다.
- 자료끼리 어긋나거나 자료와 사용자의 말이 어긋나면 추측해 고르지 않고 사용자에게 묻는다. 정한 것은 문서에 적는다.

### 3.5 고치고 지우기

- 목록에 올린 자료를 고치거나 지우면 같은 작업에서 목록 문서도 고친다. 목록의 링크가 깨지면 [문서 링크 검사기](VerificationTools.md#3-문서-링크-검사기)가 알린다.
- 자료가 바뀌어 그 자료를 근거로 쓴 문서가 어긋나면, 같은 작업에서 문서를 고치거나 이슈로 등록한다.

## 4. 기존 프로젝트 폴더 `legacy/`

- 기존 프로젝트 하나를 `legacy/<이름>/`에 통째로 복사한다. 프로젝트마다 하위 폴더 하나를 쓴다.
- 기존 프로젝트의 `.git` 폴더는 빼고 넣는다. 저장소 안의 저장소는 내용이 커밋되지 않는다. 기존 이력이 필요하면 목록 문서에 원래 저장소 주소를 적는다.
- 의존성과 빌드 산출물(`node_modules/`, `.venv/`, `build/`, `dist/`, `target/` 등)은 빼고 넣는다.
- 넣은 뒤로는 아카이브다. 커밋된 기존 프로젝트의 파일은 고치거나 지우거나 옮기지 않으며, 그 프로젝트 폴더에 새 파일을 더하지도 않는다. 기존 코드를 이어서 쓰려면 코드 루트로 복사한 뒤 거기서 고친다.
- 다른 기존 프로젝트를 더 넣는 것은 새 하위 폴더로 한다.
- 기존 프로젝트는 처음에 제품 비전, 시스템 구조, 첫 로드맵 초안의 근거가 되고([작업 관리 규칙의 첫 작업](TaskRule.md#48-첫-작업)), 그 뒤로는 예전 동작이나 결정을 확인할 때 읽는다.

## 5. 로컬 자료 폴더 `private/`

보안 때문에 저장소에 올리지 않고, 로컬에서 작업할 때만 보는 자료를 둔다.

- **git에서 뺀다**: 초기화와 갱신이 `.gitignore`에 `/private/` 줄을 넣어 둔다(없으면 더하고, 다른 줄은 건드리지 않는다). 폴더를 만들기만 하면 처음부터 git이 무시한다. 이 줄을 지우지 않는다. `private/` 아래 파일은 커밋하지도 스테이징하지도 않는다.
- **링크하지 않는다**: 어떤 문서도 `private/` 안을 링크하지 않는다. [선택 링크](DocumentationRule.md#3-링크-규칙)도 안 된다. 다른 컴퓨터와 CI에는 그 파일이 없고, 링크와 그 이름이 저장소에 남기 때문이다. 근거를 적어야 하면 경로를 인라인 코드로 적는다(예: `private/contract.pdf`). 파일 이름 자체가 민감하면 "로컬 자료"라고만 적는다.
- **목록 문서를 두지 않는다**: 목록은 커밋되므로 파일 이름이 저장소에 남는다. 에이전트는 [세션 시작 안내](#6-세션-시작-안내)로 어떤 자료가 있는지 안다. 설명이 필요하면 `private/` 안에 메모 파일을 둔다.
- **문서에는 공개해도 되는 것만 옮긴다**: 로컬 자료에서 정한 것을 문서에 적을 때는 공개해도 되는 결정만 적는다. 원문, 수치, 개인 정보, 고객 이름은 옮기지 않는다. 코드, 테스트 데이터, 커밋 메시지, PR 본문도 같다.
- **모델에는 전송된다**: `private/`는 저장소와 원격에 올라가지 않을 뿐, 에이전트가 파일을 읽으면 그 내용은 모델로 전송된다. 에이전트도 보면 안 되는 비밀(API 키, 비밀번호, 인증서)은 넣지 않는다. 그런 값은 환경 변수나 git에서 뺀 설정 파일에 두고, 에이전트에게 읽게 하지 않는다.
- 다른 컴퓨터에서 작업하면 `private/`는 비어 있다. 자료가 없어서 할 수 없는 작업이면 사용자에게 알린다.

## 6. 세션 시작 안내

참고 자료를 넣어 두고도 에이전트가 있는 줄 몰라 쓰지 않는 일을 막는다. Claude Code 세션이 시작될 때마다(재개, 맥락 압축 뒤 포함) [세션 시작 hook](VerificationTools.md#16-세션-시작-안내)이 `reference/`의 자료를 에이전트의 맥락에 넣는다. 에이전트가 폴더를 열어 볼지 기억할 필요가 없다.

- 넣는 내용: `reference/`의 자료 수, 목록 문서의 항목, 목록에 없는 자료의 경로. `private/`의 자료 수와 경로, 이 절의 주의 사항.
- 자료가 없으면 아무것도 넣지 않는다.
